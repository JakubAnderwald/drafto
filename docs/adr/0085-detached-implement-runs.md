# 0085 — Detached Implement Runs

- **Status**: Accepted
- **Date**: 2026-11-17
- **Authors**: Jakub Anderwald (with Claude Code)

## Context

`factory-agent-loop.sh` runs its modes one after another under one mutex, every 5 minutes: `--release`, `--watch`, `--browser`, `--implement`, `--plan` ([ADR-0068](./0068-factory-runs-the-board-right-to-left.md)). An `--implement` claude call runs in the foreground for up to `FACTORY_IMPLEMENT_TIMEOUT_SEC` (45 minutes). For that whole time no other mode runs for any card: no merge, no fix pass, no In Test hand-off, no planning. In the factory analysis (Oct 17 – Nov 13), #794's `--watch` waited on #821's implement that way.

The verification shell lane ([ADR-0053](./0053-pre-in-test-verification-stage.md)) and the CodeRabbit CLI lane ([ADR-0036](./0036-factory-coderabbit-cli-gap-fill.md)) already run long work detached: the tick reserves a run in the state file, spawns a supervisor in its own process group, and a later tick collects the result. Every state, git and GitHub write stays in the tick. [ADR-0084](./0084-factory-implement-deadline-and-resume.md) gave implement runs a session id, a deadline and a resume record. #849 moved everything the loop does after the claude call into `implement_handle_result()`, so a collected run can go through the same tested code, and taught `slot_acquire` to defer while `implement-lane.mjs _supervise` holds a slot.

## Decision

**Run the `--implement` claude call detached, behind `FACTORY_IMPLEMENT_DETACHED` (default `0`).** With it off, `--implement` does exactly what it did before. With it on, the loop body does everything it always did (slot, worktree, install, resume decision, the claude input), then hands the call to `implement_lane_start` and moves on to the next card. The tick ends, and the other modes run on their usual 5-minute cadence.

1. **One new module, `scripts/lib/implement-lane.mjs`.** Its subcommands are `precheck`, `start`, `_supervise`, `status`, `kill`, `finish` and `housekeeping`. A run's directory is `logs/factory/implement/<issue>-<runId>/` (mode 0700). It holds `meta.json` (`formatVersion: 1`: the argv, paths and deadlines, plus `ctx`, the handler's input globals), `input.md`, `stdout.txt`, `stderr.txt`, `supervisor.log`, `exit.json` and `collected.json`.
2. **The supervisor only runs claude.** `_supervise` runs `node run-claude.mjs -p <input> <argv>` in the worktree. It never reads or writes the state file, and never runs git or gh. It is spawned with `detached: true` and `unref()`, stdio to its log file, so launchd's process-group kill at the end of the tick doesn't reach it, and the tick's `$(…)` never waits on it. It always writes `exit.json`, a SIGKILL or a reboot excepted. A backstop at `hardKillAt` (the cap plus `FACTORY_IMPLEMENT_KILL_GRACE_SEC`, 300 s) ends a `run-claude.mjs` that didn't end at its own cap.
3. **The same call as the synchronous path.** `buildImplementArgv()` returns the synchronous call's flags (`--dangerously-skip-permissions --effort … --no-chrome --strict-mcp-config` and `--session-id`/`--resume <id>`). `buildImplementEnv()` adds the same three variables to the tick's own environment: `CLAUDE_CALL_TIMEOUT_SEC`, `CLAUDE_CALL_KILL_GRACE_SEC` and `CLAUDE_CALL_KILL_GROUP=1`. A static test pins both to the synchronous invocation in `factory-agent.sh`, and the supervisor test checks the argv and env a fake `claude` actually receives.
4. **A ledger, written only in the tick.** `implement: {runs: {"<issue>": {runId, slot, pid, sessionId, mode, startedAt, deadlineAt, hardKillAt, runDir, worktree}}}` in `factory-state.json`, through `reserveImplementRun` (refuses `running` and `max-running`), `attachImplementRun` and `finishImplementRun`. It is listed in `mergeWithDefaults`, and `state-cli.mjs factory:implement-status` prints it.
5. **Start.** In `implement_lane_start`, the tick reserves the run, writes the run dir, runs `git worktree lock`, spawns the supervisor, then attaches its pid and hands it the card's slot (`acquireSlot` with the supervisor's pid), all in one state write. A start that is refused (`max-running`, `running`, `slot-not-held`, `factory-paused`, `abandoned`) spends no attempt. One that fails with an error spends it, so a fault that repeats can't reinstall and retry forever. Either way the slot and worktree stay, and a resume that couldn't start is recorded again. The worktree and run dir are in the reservation, so a run dropped before its attach can still be unlocked. `FACTORY_IMPLEMENT_MAX_RUNNING` (1 or 2) caps the runs. `precheck` checks it, and memory pressure, after the retry-budget check, before the worktree and install are paid for.
6. **Collect, at the top of every `--implement` tick, whatever the knob.** `status` reads each ledger run: `starting`, `running`, `draining`, `overdue`, `done`, `lost`, `unattached` or `unreadable`. A run is alive while its supervisor's process group is alive (the pid with the run id on its command line, or any member of its group), while any process group below it is alive, or while a claude call carries its session id as `--session-id`/`--resume`. If `status` fails, the tick ends: no card is safe to start.
   - `running` and `starting` mark the card held, and the loop skips it before the retry-budget, disk and plan checks.
   - `draining` and `overdue` are stopped (`kill`, without finishing), read again, then collected.
   - A dead `unattached` run is dropped unread with no attempt spent (the tick died mid-start). A dead `unreadable` one is dropped unread and spends the attempt, so a card whose every run ends that way still reaches Blocked.
   - Before an ended run is handed over, the card is read again: with `factory-pause` set the result waits in the ledger; a card that left In Progress / In Review / Testing, or closed, has its run dropped unread; a card that can't be read waits a tick.
   - A `done` or `lost` run is collected. The handler's globals are restored from `meta.ctx` with safe defaults (`PRE_HEAD_KNOWN=0` when missing), the comments are fetched afresh, and `SESSION_LIMIT_NOW`, `IMPL_END_EPOCH` and `IMPL_END_ISO` are set to the run's end, for the session-limit check, the never-started check and the feedback mark (`lastFeedbackAt`/`lastImplementAt`). Then **`finish` runs before `implement_handle_result`**: the worktree is unlocked, the ledger drops the run and `collected.json` is written.
   - The exit code comes from `exit.json`. Whether a run was past its deadline is judged at its end (`exit.json`'s `endedAt`, or the supervisor's last 30-second heartbeat plus 30 s), never at the collecting tick. With no `exit.json`, a run past its deadline counts as 124. Before the deadline, the run was interrupted (a reboot, a SIGKILL): it is recorded as resumable and spends no attempt, unless it was already a resume. A run that `kill` stopped from outside counts the same way.
   - A card collected this tick waits for the next tick, as it did after a synchronous run.
7. **Guards in the other modes.** `--watch` and `--release` read the ledger (`implement_lane_held_issues`) and skip any card a run holds, until `--implement` has collected it. If the ledger can't be read, `--watch` works no In Review card and `--release` merges nothing that tick. The `--watch` cleanup sweep, `release_slot_and_worktree` and `remove_worktree_for` stop a card's run first (`implement_lane_stop`: SIGTERM, then SIGKILL a minute later). They keep the slot and worktree while anything of it is alive, and its result is not collected. `git worktree lock` is the backstop: `worktree-cli remove --force` can't remove a locked worktree. The per-mode lock and `cleanup()` are unaffected: the supervisor is node in its own session and runs no bash trap. A harness test runs the real start under a bash with an EXIT trap and a lock file.
8. **Shared helpers moved, unchanged.** `supervisorRunState` and `stopSupervisor` moved from `state-cli.mjs` into `scripts/lib/supervisor-proc.mjs`, which also gets the process-table helpers. `memoryPressure` and `freeDiskGb` moved from `verify-lane.mjs` into `scripts/lib/host-resources.mjs`.

### Races and how each is handled

- **The tick and the supervisor.** `exit.json` is written atomically (temp file and rename). A run with `exit.json` whose group is still exiting reads as `running` for its first minute after `endedAt` (the card stays held), and only then as `draining`, which is stopped. Collection needs `exit.json` _and_ nothing alive. The supervisor never writes the state file, so the tick is its only writer, as before.
- **An operator's own session.** A process outside the run's process tree counts only when it is an orphan (re-parented to launchd) carrying the run's session id as its `--session-id`/`--resume` value. An interactive `claude --resume <id>` has a shell for a parent, so it is never counted as the run or signalled. A prompt that mentions this module doesn't hide an orphan either. Because the factory therefore doesn't see such a session, the runbook requires `factory-pause` on the card (in In Progress, In Review or Testing) before resuming by hand, and its removal afterwards.
- **pid reuse.** A pid counts only with the run id on its command line. Its process group counts while any live process is in it, and POSIX never hands out a pid still in use as a group id. A session-id match needs an orphaned claude call with the id as its `--session-id`/`--resume` value, so a pager on the transcript is never signalled. Every stop (`kill`, the start rollback, the supervisor's own end-of-run cleanup) keeps the groups it found when it began (`trackRun`), and keeps signalling and polling them until each is gone, even after their ancestors have exited; membership is never re-derived from a fresh snapshot alone. A tracked group is dropped for good the first time it is empty, and a leader whose start time (`ps lstart`) differs from the one first seen is a reused id, so a later group with the same id is never signalled. The window between a snapshot and a signal is milliseconds.
- **Finish against attach.** `finish` matches the run id and the pid the caller decided on (`--pid`; `kill` passes the pid it stopped), refuses while anything of the run is alive or `ps` fails, and checks run id and pid again in the same ledger load it saves. If that last check fails after the unlock, the worktree is locked again. `implement_lane_stop` treats any `ok:false` as still alive and keeps the slot and worktree.
- **Start rollback.** A start that fails after spawning waits for the supervisor's groups to exit (run-claude's grace plus 15 s, then SIGKILL) before it drops the reservation and unlocks. If they survive, the reservation and the lock stay, and a later tick's collector stops the run.
- **Leftovers.** The supervisor follows its descendants every second while the run lives and, when claude has ended, stops any group still alive (a setsid test runner that ignored SIGTERM), so nothing the run started outlives it in the worktree. A supervisor that is itself SIGKILLed (by hand, or a stop that had to escalate) can't do that last step: a group that had already left claude's and ignores SIGTERM is then out of reach, as it is for a synchronous run (run-with-timeout.mjs). `kill` follows such groups while it runs, and the runbook says not to `kill -9` a supervisor.
- **The tick dies mid-start.** Between reserve and attach, the run is `starting` for 2 minutes, then `unattached`. A supervisor running anyway is found by its run id, stopped and dropped. A supervisor that started while the attach lost to an operator's `kill` is stopped by `start` itself (`abandoned`).
- **The tick dies mid-collect.** Before `finish`, nothing has happened, and the next tick collects again. The unlock comes first, so a crash between the unlock and the ledger write leaves a run the next tick collects again, never a locked worktree nothing unlocks. After `finish` and before or during the handler, the run's result is lost, as a synchronous run's is when the tick dies in its handler. The card stays In Progress with no attempt spent, and its next run finds the previous run's work in the worktree (the prompt's `git status` / `git log origin/main..HEAD` step).
- **Autopull between start and collect.** The loop resets the checkout to `origin/main` every tick. The running supervisor has its code in memory, and the collector reads `meta.json` and `exit.json` by `formatVersion`. A version it doesn't know reads as `unreadable` and is dropped unread. Reverting this PR while a run is live leaves the ledger in place (`mergeWithDefaults` keeps unknown top-level keys) and `slot_acquire` refusing the slot (#849), but nothing collects the run, so the runbook says to drain first.
- **An unreadable ledger.** `--watch` leaves every In Review card for the next tick (no fix, conflict, renumber or behind-main write, no In Test hand-off), and `--release` merges nothing.
- **The operator drags a card mid-run.** Collection re-reads the card before acting on a result, so a drag (or `factory-pause`) after the run ended but before its collection is honoured too. To In Review or Testing: `--watch` skips the card until the run is collected, and the handler moves it as usual. To any other column, or a closed issue: the next `--watch` sweep stops the run, discards its result, frees the slot and removes the worktree (its uncommitted changes are snapshotted, as for any removal, [ADR-0070](./0070-factory-in-test-frees-slot-and-updates-behind-prs.md)). To Approved: `--release` skips it while it's held, and the sweep then stops the run. A synchronous run went on to its handler in every one of these cases, because nothing could interrupt it.
- **The emergency stop.** `launchctl unload` and `factory:pause` stop the ticks, not a detached run: the supervisor is outside the launchd job by design. CLAUDE.md, the feature doc and the runbook say so, and name `implement-lane.mjs kill`.
- **A factory pause.** A pause (`factory:pause`, the session limit, the toolchain pause) ends every tick at its start, so nothing is collected while it lasts. An in-flight run is not stopped: it runs to its end or its cap and is collected after the pause. At a session limit the run usually fails on the same limit, and collection then pauses again until the reset read against the run's end (`SESSION_LIMIT_NOW`), not the tick's clock.
- **Repeated interruptions.** An interrupted run spends no attempt, but an interrupted resume does, so a host that keeps killing runs (jetsam, reboots) still sends the card to Blocked. A supervisor that fails before claude starts reads as exit 1 and spends the attempt, for the same reason.
- **Two runs at once** (`FACTORY_IMPLEMENT_MAX_RUNNING=2`) need two slots, and each holds its own. The ledger's count, not the slots, caps them, checked again at reserve.

## Consequences

- **Positive**: an implement run no longer stalls every other card for up to 45 minutes. Merges, fix passes, In Test hand-offs and planning keep their 5-minute cadence. The detached run makes the same claude call and goes through the same handler. Off by default, and collection runs whatever the knob, so flipping it back to 0 mid-run is safe.
- **Negative**: more moving parts — a ledger, a supervisor, process-group liveness — on a path that used to be one foreground call. An operator drag out of the factory's columns now stops a run and discards its work, which a synchronous run could never do. A tick that dies between `finish` and the handler loses that run's result. Each `--implement`, `--watch` and `--release` tick now spends a node call on `status` (with an empty ledger it never runs `ps`), and each slot release a node call on `kill`.
- **Neutral**: with the knob off nothing changes except those calls, `--now` passed to the session-limit check only while a run is collected, and the teardown helpers keeping a worktree when the ledger can't be read. Run dirs are reaped after 30 days by `implement-lane.mjs housekeeping`.

## Alternatives Considered

- **Run `--implement` in its own launchd job.** That separates it from the other modes, but two jobs then share the slots, the state file and the worktrees with no mutex between them, and the state file assumes serialized writers. The detached supervisor keeps every write in the one mutexed tick.
- **Background the call with `&` in bash.** The child would sit in the tick's process group (launchd kills it at the end of the tick), keep the bash traps' environment, and leave nothing to collect it with on the next tick.
- **Let the supervisor run the handler itself.** It would need gh, git and the state file from outside the mutex, the class of race the verification and CodeRabbit lanes were built to avoid.
- **Run up to two at once by default.** Two ultracode sessions plus their test runs press on the Mac mini's RAM; the plan decision was one at a time, with 2 allowed by the knob.
