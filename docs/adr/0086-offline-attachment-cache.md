# 0086 — Offline Attachment Cache on Mobile and Desktop

- **Status**: Accepted
- **Date**: 2026-11-18
- **Authors**: Jakub Anderwald (with Claude Code); PrimeTestLab report 10668, bug M-02

## Context

PrimeTestLab report 10668 (Android 1.4.7) found that an image attached to a note shows as a broken icon plus its file name once the device is offline. Every platform that edits notes offline does the same:

- Note content stores an image as `attachment://<storage path>`. To show it, the iOS, Android and macOS apps asked Supabase Storage for a signed URL each time a note opened (`createSignedUrl`, a network call). Offline that fails, `resolveTipTapImageUrls` leaves `attachment://`, and the editor's WebView cannot load that scheme.
- The device kept no copy: the upload queue deleted the local file after a successful upload, and images synced from other devices were never downloaded. [ADR-0010](./0010-offline-sync-strategy.md) deferred offline attachment caching to a "Phase 6" that never shipped.
- On mobile an image attached offline was inserted as `attachment://` and broke at once, though its local file existed. On desktop `buildInsertNode` awaited a signed URL with no fallback, so attaching offline inserted nothing at all.
- TenTap loads the editor from an HTML string with no base URL, so the WebView could not load a `file://` image even if one existed (Android also needs `allowFileAccess`).

A Wave 0 device spike showed that `<img src="file://…">` from the app's Documents directory renders in the TenTap WebView on the Android emulator and the iOS simulator, online and in airplane mode, once the editor gets a `file://` base URL (and `allowFileAccess` on Android). It also showed the risk: with no save-path guard, the spike's `file://` src was saved to the dev database and synced to iOS as a broken image.

The base URL turned out not to be enough on WebKit. On the sandboxed macOS app every cached image showed as a broken icon, online too, though the resolver returned the right `file://` URL and the file existed. react-native-webview turns an `html` source into `loadHTMLString:baseURL:`, and WebKit gives its web content process read access to local files only for a page loaded with `loadFileURL:allowingReadAccessToURL:` (the `uri` source plus the `allowingReadAccessToURL` prop). The iOS simulator does not sandbox WebKit's web content process the same way, which is why the spike passed there; a real iPhone is expected to fail like macOS. Android serves `file://` under `allowFileAccess` and was fine.

## Decision

Mobile and desktop keep a durable attachment cache and show cached images from it.

1. **Cache.** Only images are cached. Files live under `<Documents>/attachment-cache/<storage path>` (`ATTACHMENT_CACHE_DIR_NAME`), mapped one-to-one by `attachmentCacheRelativePath`: a storage-safe, lower-case segment is kept as it is, and any other segment gets its safe form plus `~` and a 64-bit hash of the original before the extension, so `café` / `cafe`, `photo#1` / `photo_1` or `Photo` / `photo` (on a case-insensitive disk) never share a file. Mobile uses expo-file-system, desktop react-native-fs, in mirrored `src/lib/data/attachment-cache.ts`. Downloads go to `attachment-cache/.partial/` and are moved into place once complete, one download per attachment at a time. Each download writes its own `.part` file, which it deletes when it ends, even after a sign-out wiped the cache, so a download a sign-out overtook leaves nothing in the next session's cache. A download whose signed URL was requested before a sign-out never starts (the resolver passes the cache generation it began in). On desktop the cache directory is created with `NSURLIsExcludedFromBackupKey`, set again once per launch (and after a failure to set it) before anything is written there.
2. **Picked images are the cache.** `queueAttachment` copies a picked image straight to its cache path (`copyIntoCache`), the upload reads it from there, and a successful upload keeps it (`retainInCache`). Until the attachment's row is written the file is held (`holdCacheFile`), so neither eviction nor the orphan cleanup can delete it. Any other file waits in the `attachments/` folder and is deleted once uploaded, as before. A pending image left in that folder by an earlier version is moved into the cache after its upload.
3. **Source order** (`attachment-resolver.ts`, used for note loads): a cached image gives `file://…#drafto-attachment=<URL-encoded storage path>` with no network call. Otherwise a signed URL is used and the image downloads into the cache in the background. Otherwise (offline, no copy) the src stays `attachment://`. Links and file blocks keep a signed URL: the resolver now receives `kind: "image" | "link"`, and a file referenced both as an image and as a link is resolved once per kind, so the link never gets the image's local src. A just-attached image shows its local file at once on both apps, and desktop's insert never throws.
4. **Save-path guard.** `migrateSignedUrlsToAttachmentUrls`, which every content write goes through (`serializeEditorContent`, the mobile attachment insert and the web PATCH route), maps any `file:` src carrying the `#drafto-attachment=` marker back to `attachment://<path>`. No device path can be stored or synced. A note opened with local srcs and not edited still serialises to its stored content, so the #654 no-op-save baseline holds.
5. **WebView.** On Android, TenTap loads its page from its HTML string with `webviewBaseURL`, the Documents directory as a `file://` URL, and `allowFileAccess` on. On iOS and macOS (WebKit) the page loads from a file instead, so WebKit grants read access to the cache:
   - **Page file.** `ensureEditorPage` (`src/lib/editor-page.ts`, mirrored) writes TenTap's own page (`editorHtml`, exported by `@10play/tentap-editor`, the HTML it would otherwise load as a string; nothing is copied into the repo) to `attachment-cache/.editor/editor-<hash>-<length>.html` (`editorPageFileName`, shared). The name changes with the HTML, so a TenTap upgrade writes a new file and older ones are deleted; an unchanged page is never rewritten. It is written as `<name>.tmp` and moved into place, so a half-written page is never loaded. The editor checks the file each time it mounts and writes it if missing (a sign-out deletes the whole cache), off the render path: `useEditorPage` runs it in an effect and the WebView mounts once it settles.
   - **Read-access scope.** The WebView gets `source={{ uri: <page file> }}` and `allowingReadAccessToURL` = the `attachment-cache/` directory: the narrowest directory holding both the page and every image the resolver hands out (cached images and just-picked ones are all in the cache). The rest of Documents (the database, the `attachments/` upload folder) stays unreadable. `.editor` starts with a dot, which no cached attachment's name does (`attachmentCacheRelativePath`), and the cache's walk skips it like `.partial` and `.index.json`, so the page is never indexed, counted against the cap, evicted or swept as an orphan; the sign-out wipe deletes it with the rest, and the next editor writes it again.
   - **Boot.** With a `source` prop, TenTap stops inlining its boot script and passes it as `injectedJavaScriptBeforeContentLoaded` (and injects it again on load), so the bridge, initial content, dynamic height and the injected scripts (find bar, render status) work as before.
   - **Fallback.** If the page can't be written (on desktop, whose file calls are asynchronous, also when the write takes over 3 s; on mobile the write is synchronous), or the file fails to load before it first loads, the editor logs it and loads its page inline as before (html + base URL), where cached images may not show; it never waits on the file forever. The `source` key is then left out, never set to `undefined`, which would replace TenTap's own source.
   - **Everywhere.** `originWhitelist` adds `about:`, `file:` and `data:`, and `allowFileAccessFromFileURLs` / `allowUniversalAccessFromFileURLs` stay off, so the page can load images but script cannot read files.
6. **Prefetch.** After each successful sync pass, `prefetchAttachmentImages` downloads up to 25 not-yet-cached images (100 MB in all) of notes not in the trash, newest first, on any network. Images over 20 MB are cached only once viewed. A pass never fills the cache past its cap, so prefetching never evicts anything and never refetches what an eviction removed. A pass that found nothing is not repeated for a minute; one that stopped on a failure, or that its session's end cut short, is. A call never joins a running pass whose session has ended.
7. **Index and eviction.** The cache is capped at 300 MB on mobile and 1 GB on desktop. An in-memory index (`AttachmentCacheIndex`, shared) holds each file's size and last use and the running total. One walk of the directory fills it on first use; writes and deletes keep it current, so eviction and prefetch never walk the directory again, and eviction does nothing while the total fits. When each file was last used is saved, two seconds after a change, to `attachment-cache/.index.json`, so the order survives a restart; a file the index doesn't know falls back to its modification time. Over the cap, the least recently used files go first. A file whose attachment is `pending`, `failed` or `quota_exceeded`, or one still held, is never evicted: it is the only copy. A call made while an eviction runs makes it run once more, so a file written meanwhile is counted. A file that can't be deleted stays in the index, so a later pass retries it.
8. **Orphan cleanup.** After the first sync of a session, `cleanupOrphanedFiles` also runs `removeOrphanedCacheFiles`: a cached file whose attachment row is gone, whose note no longer exists locally (deleted permanently on this device; sync doesn't pull permanent deletions made elsewhere, so a note deleted elsewhere keeps its images until it is deleted here, they are evicted or the user signs out) or that isn't an image is deleted. A note in the trash can be restored, so it keeps its images. Leftover `.partial` downloads go too, but never the file of a download still running.
9. **Sign-out.** `deleteAllLocalAttachments`, which sign-out and the cross-account identity guard already call, also deletes the cache and drops a running prefetch pass. Work still running for the old account is thrown away instead of landing in the next account's cache: on desktop, where every file call is asynchronous, each change after an await first checks the cache wasn't wiped meanwhile, and never recreates the cache folder.
10. **Render status (E2E builds only).** A script injected into the editor reports, per image, `img.complete && img.naturalWidth > 0` and its height on screen. The app mirrors it in invisible, untouchable accessible views (`testID` `editor-image-rendered` / `editor-image-missing`, label "Image shown: <name>" / "Image not loaded: <name>"), which the E2E checks read because the WebView's own image nodes do not reliably reach the accessibility tree. VoiceOver and TalkBack would read them to real users, so they exist only in a build made with `EXPO_PUBLIC_E2E_PROBES=1` (mobile) or `E2E_PROBES=1` (desktop); see [testing.md](../architecture/testing.md#e2e-probe-builds).
11. **Resolve bound.** Each attachment reference in a note has its own 8 s bound (`withResolveTimeout`): one that hangs on a network with no internet stays `attachment://`, while cached images keep their local src.

The privacy policy says attachments stay on the device for offline viewing and are erased on sign-out.

## Consequences

- **Positive**: images open offline on iOS, Android and macOS, including right after a cold start and right after being attached offline. Desktop can attach offline. The save-path guard also protects the web PATCH route from any client sending a local src.
- **Positive**: the cache, the source order and the policy are mirrored between the two apps; eviction and prefetch decisions, the index and the prefetch pass itself live in `@drafto/shared` (`planAttachmentCacheEviction`, `selectPrefetchCandidates`, `AttachmentCacheIndex`, `createAttachmentPrefetcher`).
- **Negative**: the apps use more device storage, up to the cap plus files not yet uploaded. Prefetch uses data on cellular too.
- **Negative**: a view or write in the last two seconds before the app is killed may miss the saved index, and then counts from the file's modification time.
- **Negative**: Android Auto Backup and iCloud backup still include the mobile cache. expo-file-system has no exclude-from-backup call, and excluding the folder on Android means replacing the backup rules expo-secure-store installs. Desktop excludes it from Time Machine.
- **Negative**: on iOS and macOS the editor's page is a ~600 KB file in the cache, written once per TenTap version (and again after each sign-out), and the editor's first mount waits for that check. If writing or loading it fails, cached images break as before the fix, with a logged warning.
- **Neutral**: non-image attachments (opening a PDF offline) are still opened through a signed URL; a follow-up covers them. The WebKit fix (page file plus read access to `attachment-cache/`) is covered by unit tests only: it must be confirmed on the macOS app and a real iPhone, since the iOS simulator does not reproduce the sandbox.

## Alternatives Considered

- **`data:` URIs for cached images.** Rendered in the spike too, but every `getJSON` round-trip and autosave would carry the base64 image. Kept only as a fallback, not needed.
- **Relying on the WebView's HTTP cache.** Each signed URL carries a new token, and offline no URL can be created, so nothing ever hits the cache.
- **Storing local paths in note content.** A device path is broken on every other device, and the spike showed it spreading through sync. The fragment marker keeps the canonical `attachment://` form in storage.
- **A new database column for the cached path.** Would need a mirrored schema migration on both apps; the cache is keyed by `file_path` instead, so no schema changes.
- **Caching in `Paths.cache` / `Library/Caches`.** Out of backups, but the OS can purge it, and pending uploads also need a durable home.
- **Read access to the whole Documents directory**, with the page file beside the cache. Works too, but would let the editor's page load any file in Documents (the database included); `attachment-cache/` holds everything the editor needs.
- **A forked or patched TenTap, or a copy of its bundle in the repo.** TenTap already supports a `source` prop and exports `editorHtml`, so the page is written from the installed package and follows its upgrades.
- **Keeping the inline page on WebKit and inlining images as `data:` URIs.** See above: every save round-trip would carry the images.
