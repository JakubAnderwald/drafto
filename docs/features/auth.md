# Authentication

**Status:** shipped **Updated:** 2026-10-25

## What it is

Email+password and OAuth (Google, Apple) sign-in backed by Supabase Auth, gated by an admin-approval step before a new user can reach the app. Row-Level Security (RLS) on every user-scoped table enforces that only approved users can read or write their own data.

## Current state

Available on all four platforms: web, iOS, Android, and macOS. The web app uses Next.js middleware for session refresh and the approval gate; the mobile and desktop apps use an `AuthProvider` context that checks `profiles.is_approved` on boot and refreshes on resume. Email confirmation is enabled in Supabase Auth, so an email sign-up ends on a "Check Your Email" screen rather than in the app (see [Sign-up and email confirmation](#sign-up-and-email-confirmation)); OAuth providers are configured for Google and Apple. The first admin (`jakub@anderwald.info`) is bootstrapped via migration; all other accounts start unapproved and land on a waiting-for-approval screen until an admin flips `profiles.is_approved`.

A signed-in user can permanently delete their own account from inside the app on every platform: web `/settings`, the mobile Settings tab, and the desktop sidebar's app menu (⋯). Each one asks the user to type `DELETE`, then calls `DELETE /api/account` on the web app, which removes the user's attachment files, auth user and every row. Mobile and desktop then wipe their local database. The public page [drafto.eu/account/delete](https://drafto.eu/account/delete) explains the same steps to signed-out visitors, with `support@drafto.eu` as the email fallback. On iOS, an Apple-linked user also confirms with Apple, and the server revokes their Sign in with Apple tokens once the account is gone. Web, Android and macOS do not revoke yet ([#705](https://github.com/JakubAnderwald/drafto/issues/705)); see [Sign in with Apple token revocation](#sign-in-with-apple-token-revocation).

## Cross-platform notes

- **Web** is the only platform with a session-refresh middleware; it also enforces the `is_approved` gate server-side before any page renders. This is the canonical gate — it cannot be bypassed by client-side tampering.
- **Mobile and desktop** run in an offline-first model and cannot rely on a middleware. They check `profiles.is_approved` via `AuthProvider` on sign-in, app resume, and pull-to-refresh. A cached approval flag (`approval-cache`) lets the app continue to work offline once a user has been approved at least once.
- **OAuth flows differ per platform and provider** — the web `/auth/callback` route is used by the **web app only**:
  - **Web (both providers)** — `signInWithOAuth()` PKCE redirect, returning to `/auth/callback`, which calls `exchangeCodeForSession()`.
  - **Google on iOS and Android** — the native Google Sign-In SDK; the returned ID token goes straight to `supabase.auth.signInWithIdToken()` (`apps/mobile/src/lib/oauth.ts`). No `expo-web-browser` session and no `/auth/callback` route — but the two platforms differ underneath: on **Android** the flow is fully native (the Play services account picker), while on **iOS** `GIDSignIn` still presents Google's own system web sheet and returns through the reversed-client-ID URL scheme (`EXPO_PUBLIC_GOOGLE_IOS_URL_SCHEME`, registered by the config plugin in `apps/mobile/app.config.ts` — it is load-bearing, not dead config). The Android leg additionally requires an Android-type OAuth client registered by package name + signing-cert SHA-1 — see [builds and releases](../operations/builds-and-releases.md#google-sign-in-android-oauth-client).
  - **Apple on iOS** — `expo-apple-authentication`'s system sheet, then `signInWithIdToken()`. Genuinely web-free: no browser and no web sheet at any point.
  - **Apple on Android** — `signInWithOAuth()` opened via `expo-web-browser`, handed back to the app through the `drafto://auth/callback` deep link, and the PKCE `code` exchanged in-app. The callback is parsed by `apps/mobile/src/lib/app-deep-link.ts`, not React Native's `URL`. Before the mobile client switched to PKCE ([ADR-0045](../adr/0045-mobile-auth-uses-pkce.md)) no code came back, so this leg most likely signed nobody in.
    - The redirect reaches a running app twice: `openAuthSessionAsync` resolves with it, and Expo Router hears the same `Linking` event. `app/+native-intent.tsx` claims the router's copy and returns `null`, so the router never navigates to it. Before that, the router showed "Unmatched Route" on top of a sign-in that had worked.
    - Both copies go through `completeAuthCallback` (`apps/mobile/src/lib/auth-callback.ts`), which exchanges each code once per process. auth-js deletes the PKCE verifier after the first attempt, so a second exchange could only fail.
    - The router's copy is the only one when Android killed the app while the user was on Apple's page, or when the session resolved as "dismiss" because the app came to the foreground before the redirect. The code is still exchanged, and a failure is held for the login screen in `apps/mobile/src/lib/auth-callback-errors.ts` until a new sign-in starts or one succeeds. It is held as state rather than sent as an event, because after a cold start the login screen can mount twice while the router settles. It is always the generic message, never the link's `error_description`: with no sign-in in progress, any website or app could have sent the link. The router's copy decides whether to report only once the outcome is known and no browser sign-in is open. If the session took the same redirect, it reports the outcome itself, so the error is not shown twice. If it closed without seeing the redirect, the router's copy reports it.
  - **macOS (both providers)** — `signInWithOAuth()` opened in the system browser with `redirectTo` set to the drafto.eu hand-off page `https://drafto.eu/auth/desktop/callback` ([ADR-0044](../adr/0044-desktop-auth-web-handoff.md)). That page forwards the code to the `eu.drafto.desktop://auth/callback` deep link (`apps/desktop/src/lib/oauth.ts`), where it is exchanged in-app, and leaves the tab on a "Finishing sign-in in Drafto — you can close this tab" page. Redirecting straight to the scheme used to leave Google's page frozen mid-navigation. The page never exchanges the code itself, because the PKCE verifier lives in the app.
    - The page opens the app on its own only on a Mac desktop.
    - It shows fixed copy, never Supabase's error text.
    - The app exchanges each code once, so the page's "Open Drafto" button cannot re-send a spent code.
    - The app ignores `access_token`/`refresh_token` in the URL: any website can open the scheme, so only a PKCE code is a credential.
    - The hand-off URL, code included, can appear in Sentry traces and replays. That is acceptable because the code is useless without the app's `code_verifier`.
    - The `code_verifier` comes from `SecRandomCopyBytes`, and the challenge is S256 ([ADR-0062](../adr/0062-desktop-pkce-native-csprng.md)). Hermes has no global `crypto`, so `apps/desktop/src/lib/crypto-random.ts` installs one from the in-project `DraftoCrypto` native module: `getRandomValues` before the client is created, and `subtle` once a native SHA-256 self-test passes. OAuth sign-in, sign-up and the reset-link request await `cryptoReady` from `apps/desktop/src/lib/supabase.ts` first, so a flow started right after launch still gets S256. The self-test gives up after 5 seconds, so a hung native call delays sign-in by at most that long. Without the module (Jest, CI), supabase-js falls back to a `Math.random()` verifier and a `plain` challenge. The module is compiled from the Xcode project, not `node_modules`, so it is safe for the [fossil build](../operations/desktop-build-fossil.md).
  - **Google's account chooser names the app from the Branding page** of the Cloud project, but only once it is verified; until then it shows the Supabase redirect host (`tbmjbxxseonkciqovnpl.supabase.co`). See [Google OAuth branding](../operations/builds-and-releases.md#google-oauth-branding).
- **The native ID-token legs depend on two Supabase Auth provider settings.** They must be set in **both** projects: prod `tbmjbxxseonkciqovnpl` and dev `huhzactreblzcogqkbsd`. Nothing in the repo or CI can see them. Both were found missing on 2026-10-10, when iOS 1.4.3 was first tested on a device.
  - **Apple → Client IDs** must be `eu.drafto.web.auth,eu.drafto.mobile`, in that order.
    - The browser flows (web, macOS, Apple on Android) send the **first** entry as Apple's `client_id`, so the Services ID must stay first.
    - The native iOS sheet issues tokens whose audience is the bundle ID `eu.drafto.mobile`.
    - Without the second entry, iOS Apple sign-in fails with "Unacceptable audience in id_token: [eu.drafto.mobile]".
  - **Google → Skip nonce check** must be on.
    - The iOS Google Sign-In SDK embeds a nonce in the ID token that the app can't read, and `@react-native-google-signin` (16.x, free API) can't pass its own.
    - With the check on, iOS Google sign-in fails with "Passed nonce and nonce in id_token should either both exist or not".
    - The trade-off is that Supabase no longer binds Google ID tokens to a nonce. The audience (the Web client) and signature checks still apply.
    - Revisit if the library gains nonce support.
  - Read or change both in the dashboard (Authentication → Sign In / Providers) or through the Management API (`GET/PATCH /v1/projects/<ref>/config/auth`):
    - Apple: set `external_apple_client_id` to `eu.drafto.web.auth` and `external_apple_additional_client_ids` to `eu.drafto.mobile`. The platform merges the additional IDs into `external_apple_client_id`, so a `GET` reads back `"eu.drafto.web.auth,eu.drafto.mobile"` and an empty additional field. Sending the comma-joined list in `external_apple_client_id` alone is equivalent.
    - Google: set `external_google_skip_nonce_check` to `true`.
- **The browser Apple flows depend on a client secret that expires.** Supabase's Apple provider holds a **Secret Key**: an ES256 JWT signed with the Sign in with Apple key `7BS35Y82Q6` (team `4J2USPSG2U`, subject the Services ID `eu.drafto.web.auth`). Apple refuses any secret that lives longer than 6 months.
  - When it lapses, web, macOS and Apple-on-Android sign-in fail with "Unable to exchange external code", and the Supabase auth log shows `oauth2: "invalid_client"` on `/callback`. Native iOS sign-in sends an ID token, needs no secret and keeps working, so the outage is easy to miss. That is how the first secret failed on 2026-10-10, most likely 180 days after it was made with the key on 2026-04-13.
  - The current secret was generated on 2026-10-10 and **expires on 2027-04-08**. Rotate it about a week before.
  - To rotate:
    1. Run `node scripts/apple-client-secret.mjs --out <file>`. It signs with `~/drafto-secrets/AuthKey_7BS35Y82Q6.p8` and writes the secret to `<file>` (mode 0600) without printing it.
    2. Set it as **Authentication → Sign In / Providers → Apple → Secret Key** in both projects, prod `tbmjbxxseonkciqovnpl` and dev `huhzactreblzcogqkbsd`. Or send it through the Management API, which keeps it out of the terminal and prints only the HTTP status (expect `200`): `jq -n --rawfile s <file> '{external_apple_secret: $s}' | curl -sS -o /dev/null -w "%{http_code}\n" -X PATCH https://api.supabase.com/v1/projects/<ref>/config/auth -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" -H "Content-Type: application/json" --data @-`.
    3. Delete `<file>`, then sign in with Apple on drafto.eu. Only a real sign-in proves the secret: Apple's token endpoint rejects a dummy code before it checks the client, so it answers `invalid_grant` even for a garbage secret.
    4. Update the expiry date above.
  - The `.p8` key itself does not expire, but Apple lets you download it only once. If it is lost or revoked, create a new key under Certificates, IDs & Profiles → Keys with Sign in with Apple enabled for the App ID `eu.drafto.mobile`, then pass `--key` and `--key-id`.
  - The same key is also in Vercel as `APPLE_SIGN_IN_KEY_ID` and `APPLE_SIGN_IN_PRIVATE_KEY`, where the web API signs its own short-lived secrets to revoke Apple tokens on account deletion ([Sign in with Apple token revocation](#sign-in-with-apple-token-revocation)). Those secrets last 5 minutes and are made per deletion, so they never need rotating. A new key must be updated there too, in Production and Preview.
- **Password recovery is deep-linked on mobile and desktop** ([ADR-0034](../adr/0034-password-recovery-deep-links-on-mobile-and-desktop.md)). Web redirects to `/auth/callback?next=/reset-password`; the apps cannot, so `resetPasswordForEmail` targets the app instead — `drafto://reset-password` (mobile) and, on desktop, the hand-off page `https://drafto.eu/auth/desktop/recovery`, which forwards the code or error to `eu.drafto.desktop://auth/recovery` and tells the user the link only works on the Mac that asked for it ([ADR-0044](../adr/0044-desktop-auth-web-handoff.md)). These URLs, plus `https://drafto.eu/auth/desktop/callback` for desktop OAuth, must be allowed in **Supabase Auth → URL Configuration → Redirect URLs** for the dev (`huhzactreblzcogqkbsd`) _and_ prod (`tbmjbxxseonkciqovnpl`) projects, or Supabase rejects the redirect and falls back to the Site URL. Both hosted projects already allow `https://drafto.eu/**`, which covers the two hand-off pages. Keep the old `eu.drafto.desktop://auth/callback` and `eu.drafto.desktop://auth/recovery` entries too: installed builds still send them. Both apps run PKCE ([ADR-0045](../adr/0045-mobile-auth-uses-pkce.md)), so a reset link only completes on the device that requested it. On desktop, any other device gets a hand-off page that says so instead of opening the app; on mobile, the request screen says to open the link on this device. Both apps accept only a `code` from a recovery link and never read `access_token`/`refresh_token`: any website or app can open their schemes, so a token-only link gets the missing-credentials error instead of signing the app into someone else's account. Supabase times a PKCE reset from when it was requested, so the link expires with the server's flow-state window (5 minutes by default), not the email link's 1-hour OTP expiry.
- **A recovery session is a real session**, which is why both apps carry an `isRecovering` flag on `AuthProvider`. It is checked _before_ the approval gate and before the signed-in redirect, or the reset screen is unreachable. The flag is set by the deep-link handler the moment a recovery link arrives, before the code exchange. On mobile (supabase-js 2.116) the exchange then also emits `PASSWORD_RECOVERY` for a recovery code, and `AuthProvider` handles that event too. The desktop fossil build ships auth-js 2.101.1, which emits `SIGNED_IN` even for a recovery code, so on macOS the deep-link handler alone holds the reset screen.
- **Account deletion is the one auth flow where mobile and desktop call the web API.** Everything else they do goes straight to Supabase. (Desktop OAuth and password-reset redirects pass through drafto.eu pages in the browser, but the app itself never calls them.) Deleting an auth user needs the service role, which must never ship in a client, so the native apps send their Supabase access token to `DELETE /api/account` on the web origin (`EXPO_PUBLIC_API_URL` / `API_URL`, falling back to `https://drafto.eu`). See [Account deletion](#account-deletion) and [ADR-0038](../adr/0038-account-deletion-endpoint.md).
- **Shared invariant:** RLS in Postgres is the single source of truth. Every platform uses the same `profiles.is_approved` column and the same RLS policies — if a user bypasses a client check, the database still refuses the query.

## Sign-up and email confirmation

Email confirmation is on in both Supabase projects, so `supabase.auth.signUp()` returns a user and **no session**, and no `SIGNED_IN` event fires. Every platform checks `data.session` and, when it is `null`, swaps the form for a "Check Your Email" state showing the address and `SIGNUP_CONFIRMATION_SENT`, with a "Back to login" control. The form is gone, so it cannot be resubmitted for a second email. Before this, mobile replaced to the waiting screen and the route guard bounced the user straight back to Log In; web pushed to `/waiting-for-approval`, which the middleware also bounced; and desktop just stopped its spinner (#675). All three looked like a silent failure (App Review recording, 0:36–0:51).

- **The copy is neutral on purpose.** For an address that already has an account, Supabase sends no email and answers exactly as for a new one: a user with `identities: []` and no session. The copy says "If this address is new to Drafto, we've sent it a link…" and tells existing users to log in, so it never claims an account was just created and never reveals whether one exists.
- **Where the link lands.**
  - **Mobile and desktop** pass `emailRedirectTo: SIGNUP_EMAIL_REDIRECT_URL` (`https://drafto.eu/login?confirmed=1`). Supabase confirms the address when the link is opened, then appends the app's PKCE `code`, which a browser cannot use. The web login page ignores the code and shows `EMAIL_CONFIRMED` ("Email confirmed. Log in to continue, here or in the Drafto app."). `/login` is not a universal or app link, so the link always opens the browser.
  - **Web** keeps `emailRedirectTo: <origin>/auth/callback`. In the browser that signed up, the callback exchanges the code and the user lands signed in, on the waiting screen. In any other browser the exchange fails and the callback redirects to `/login?error=auth-callback-error`. The login page now shows a fixed explanation for that (`AuthCallbackErrorNotice`), which disappears once the user submits the form. The address is confirmed either way.
- **When sign-up does return a session** (confirmation turned off, e.g. a local Supabase), behaviour is unchanged: mobile and desktop route through the auth state change, and web pushes to `/waiting-for-approval`.
- **Operator check.** `https://drafto.eu/login?confirmed=1` must be allowed under Supabase Auth → URL Configuration → Redirect URLs in dev and prod. Both allow `https://drafto.eu/**`, which covers it. If it were missing, Supabase would fall back to the Site URL and the user would land on drafto.eu without the notice.

## Approval checks on mobile and desktop

`checkApproval` sets `isCheckingApproval` for the length of its `profiles` query. It runs at launch, on every sign-in, and from "Check approval status" on the waiting screen.

- **A check in flight holds routing; it does not blank the app.** Mobile's `RouteGuard` and desktop's `RootNavigator` show the full-screen spinner only for `isLoading`. `isLoading` stays `true` through the launch-time check, so nothing is routed on a stale approval at start-up. During any later check, mobile keeps its stack mounted and skips the routing effect, and desktop keeps rendering the screen it last settled on. Before this, a manual check swapped the waiting screen for an unthemed spinner page and remounted it, so its "still pending approval" message was lost (App Review recording, 1:12; #676). On sign-in the login screen stays up during the check, so an approved user never sees the waiting screen flash and an unapproved one never sees the app. A signed-out user is never held: a check still in flight cannot keep them in the app. A recovery link is routed straight away, because the reset screen does not depend on approval. The loader uses `semantic.bg` on both platforms.
- **Only the latest approval check counts.** Because the login screen stays usable during a check, a second sign-in can overtake the first one's check. Each check takes a number from `approvalCheckRef`, and only the latest may set `isApproved` or clear `isCheckingApproval`. A session ending (`SIGNED_OUT`, `resetLocalSession`) bumps the number and clears the flag, so a late result for an earlier account never routes the current one.
- **The hourly token refresh does not re-check an approved user.** `onAuthStateChange` skips `checkApproval` on `TOKEN_REFRESHED` when the session's user is the one the last check found approved (`approvedUserIdRef`). A refresh only swaps tokens, and RLS still enforces approval on the server. An unapproved user is still re-checked on each refresh, so a user left on Awaiting Approval moves on once approved, and a launch-time check that failed offline gets another try. Every other event with a session (`SIGNED_IN`, `USER_UPDATED`, a refresh carrying a different user) still checks, and sign-out clears the ref. The trade-off: revoking an approved user takes effect at their next sign-in or launch rather than within the hour, while their data access is cut by RLS straight away.
- **Mobile navigation never stacks a second login.** The guard's signed-out branch, the "Log in" / "Back to login" links on sign-up and forgot-password, and the reset screen's exits all use `dismissTo("/(auth)/login")`. It pops back to a login screen already in the stack, or replaces the current screen when there is none. Replacing used to leave `[login, login]`, which showed a "‹ Log In" back button on Log In (recording, 0:38–0:58). `(auth)/login` sets `animationTypeForReplace: "pop"`, so signing out reads as going back rather than as a push.
- **Mobile auth headers.** Every auth screen has a body heading, so its header title would repeat it. Log In, Reset Password and Awaiting Approval hide the header (`headerShown: false`), and the last two also disable the back swipe. Sign Up and Forgot Password keep an empty header (`headerTitle: ""`) for the back button. The `title` options stay, because iOS uses them as the back label. With no header to reserve the space, the three header-less screens pad their own content by the safe-area top inset (`useSafeAreaInsets`), so it stays clear of the status bar and notch when the keyboard or a large text size scrolls it. Maestro waits for the body headings ("Log In"), not the headers.

## Sign-out with unsynced changes

Signing out wipes the local database, and the provider's own pre-sign-out flush is best-effort: it gives up after 10 s and then discards whatever did not sync (App Review recording, 2:59, signed out with "3 pending changes"). Mobile Settings and the desktop app menu therefore sign out through `useSafeSignOut()`:

1. The button shows a loading state: the Settings button spins, and on desktop the sidebar's user row reads "Signing out…" and swaps the ⋯ trigger for a spinner. A second press is ignored. Sign-out and account deletion never overlap, because both wipe the device: on mobile the Delete account row is disabled meanwhile; on desktop an open delete panel stays mounted (a deletion already in flight keeps its progress and result) but cannot be confirmed, and "Sign out" does nothing while a deletion request is in flight.
2. It writes any edit still inside an editor's save debounce (`flushPendingSaves`: every mounted `useAutoSave` registers its `flush`, which also waits for a save already writing). Otherwise that edit would be neither counted nor synced.
3. It counts unsynced changes straight from WatermelonDB (`countUnsyncedChanges`): created and updated rows plus pending deletions in notebooks, notes and attachments, and attachments whose row synced but whose file is still `pending` or `failed` to upload. Sign-out deletes local files, and for those that is the only copy. If there are none, it signs out.
4. Otherwise it awaits one more `sync()`, bounded to 10 s by the shared `withTimeout`, and counts again. The provider's `sync()` joins a sync that is already running and never rejects ([ADR-0048](../adr/0048-local-writes-trigger-debounced-sync.md)), so this one await also covers a push that was in flight when the user pressed Sign Out.
5. If changes are still pending (offline, or the sync failed), it asks "Sign out?" with "N changes haven't synced and will be lost." and **Cancel** / **Sign out anyway** (destructive). Only "Sign out anyway" signs out.

Having just synced and counted, the hook calls `signOut({ skipFinalSync: true })`, so the provider does not spend up to another 10 s repeating a sync whose outcome is known. If the count itself fails, it signs out unwarned with the provider's flush, as before, rather than trap the user in the account. If sign-out throws, the user gets a "Couldn't sign out" alert and stays signed in. The waiting screen's and the reset screen's "Sign out" buttons still call `signOut()` directly, since an unapproved or recovering user has nothing to sync.

The count is its own definition, not the "N pending changes" the sync status shows: that number leaves out pending deletions and uploads. Folding the provider's `checkPendingChanges` onto `countUnsyncedChanges`, so the two numbers agree, is a follow-up.

## Account deletion

A signed-in user deletes their own account immediately and permanently. There is no soft delete, grace period or undo, and no export step inside the flow. The design is recorded in [ADR-0038](../adr/0038-account-deletion-endpoint.md).

### Flow per platform

Every platform uses the same copy: the "Delete account" label, the warning "This permanently deletes your Drafto account and all of your notebooks, notes and attachments. This cannot be undone.", the "Type DELETE to confirm" prompt, and `describeAccountDeletionFailure(result)` for errors. The confirm button is enabled only when `input.trim() === ACCOUNT_DELETE_CONFIRMATION` (case-sensitive) and no request is pending.

- **Web.** `DeleteAccountSection` is the last card on `/settings`. Its danger button opens an inline `ConfirmDialog` ("Delete your account?") that contains the warning and the confirmation `Input`, gated through `confirmDisabled`. Confirming calls `requestAccountDeletion({ baseUrl: "" })`, a same-origin request authenticated by the session cookie.
  - On `ok` it calls `createClient().auth.signOut({ scope: "local" })`. A sign-out error goes to Sentry (`delete-account-section:signOut`) and does not stop the flow. It then calls `router.replace("/login?deleted=1")`, where `AccountDeletedNotice` shows "Your account has been deleted."
  - Any other result shows the failure copy inside the dialog. Nothing is signed out, and the user can retry.
- **iOS and Android.** The Settings tab has a "Delete account" row (`delete-account-row`) below Sign Out. It opens `DeleteAccountDialog`, an RN `Modal` with `delete-account-input`, `delete-account-confirm` and `delete-account-cancel`, and passes `useAuth().deleteAccount` as `onConfirm`.
  - While `useNetworkStatus()` reports offline (`isConnected` is false, or `isInternetReachable` is explicitly false), the row is disabled and "Deleting your account needs an internet connection." is shown. Unknown reachability (`null`) keeps it enabled.
  - Failures are shown inline and the dialog stays open. On `ok` the provider raises the account-deleted notice (`apps/mobile/src/lib/account-deleted-notice.ts`), then clears the session, and the route guard in `apps/mobile/app/_layout.tsx` sends the user to login. Login shows `ACCOUNT_DELETED_MESSAGE` ("Your account has been deleted.", shared with web) in a success banner until the next sign-in attempt or a successful sign-in. Before this, login gave no sign that anything had happened (App Review recording, 3:27).
  - **iOS, Apple-linked users.** The dialog adds: "You use Sign in with Apple, so Apple will ask you to confirm. This lets Drafto stop using your Apple ID. If you cancel that step, your account is still deleted." (`delete-account-apple-notice`). Confirming opens Apple's sheet before the request is sent. See [Sign in with Apple token revocation](#sign-in-with-apple-token-revocation).
- **macOS.** Account actions sit behind the app menu, so they cannot be clicked by accident. The user section at the bottom of the sidebar (`notebooks-sidebar.tsx`) shows the email and a ⋯ button (`app-menu-trigger`, label "App menu"). It opens `AppMenu` (`app-menu.tsx`) upward, mirroring the web app menu but listing only what macOS has: "Sign out" (`logout-button`), a separator, and "Delete account…" (`delete-account-menu-item`). Theme stays in the native View ▸ Appearance menu. Choosing "Delete account…" closes the menu and opens `DeleteAccountPanel` inline in the user section, and its confirm button is the final click. The panel uses the same test IDs as mobile.
  - On `ok` the desktop provider raises the same notice (`apps/desktop/src/lib/account-deleted-notice.ts`), and the login screen the navigator shows next carries the "Your account has been deleted." banner.
  - Choosing "Delete account…" only ever opens the panel, never toggles it. Closing goes through the panel's Cancel or Escape, which stay disabled while a request is pending, so the panel cannot unmount mid-request.
  - `AppMenu` hosts the whole sidebar through a render prop (`trigger`, `onAnchorLayout`) and renders its transparent backdrop and menu as the last children of that host, positioned from the user section's measured height. On react-native-macos a view laid out outside its parent's bounds is not reliably hit-testable, so nothing clickable may overflow its parent. The menu closes on the trigger, on choosing an item, on Escape (it takes keyboard focus when it opens), or on a click anywhere else in the sidebar. Its backdrop only covers the sidebar, so a click in the note list or editor leaves the menu open. Closing on those clicks would need a window-wide backdrop in `apps/desktop/src/screens/main.tsx`.
  - The panel and menu are inline rather than a `Modal`, because `Modal` is unproven on the react-native-macos fossil build.
  - Offline (same `isConnected` / `isInternetReachable === false` rule as mobile), "Delete account…" is disabled and the offline note is shown under it inside the menu, and the panel's confirm is disabled too. On `ok`, `app-navigator.tsx` renders the login screen once the session is null.
- **Public page.** `/account/delete` works signed out. It lists the in-app steps for each platform, what is deleted (account, notebooks, notes including trash and edit history, attachments, API keys), and what may be kept outside the account (Sentry error reports and Vercel request logs until those services delete them, support emails, administrator notification emails about the sign-up or support requests, GitHub issues filed from support emails, and the local copy on devices that were not signed out before the deletion — the page says to sign out of other devices first, or uninstall the app there afterwards). It also gives the `support@drafto.eu` fallback for people who no longer have the app. `/support` and `/privacy` link to it from their footers.

### The endpoint and its authentication

`DELETE /api/account` (`apps/web/src/app/api/account/route.ts`) reads no query string and no params. Its only body is an optional Apple revocation grant, `{ "apple": { "authorizationCode", "clientId" } }` ([below](#sign-in-with-apple-token-revocation)), which can never name an account. The user id comes only from a verified credential, through `authenticateAccountRequest(request)`, which returns the verified Supabase user:

- **An `Authorization` header is present** (mobile and desktop). It must be exactly `Bearer <Supabase access token>`, verified with `createAdminClient().auth.getUser(token)`. A header that is missing a token, uses another scheme, or carries an invalid token gets 401, with **no cookie fallback**. A Drafto MCP API key is not a Supabase access token, so it gets 401 as well.
- **No `Authorization` header** (web). The session cookie is verified with the server client from `@/lib/supabase/server` and `auth.getUser()`.

Both `/api/account` and `/account/delete` are in `PUBLIC_ROUTES` in `apps/web/src/lib/supabase/middleware.ts`. Native clients send no cookie, so without that entry middleware would answer 307 to `/login`, and `fetch` would follow it to a 200 HTML page. Being public makes the route responsible for its own authentication. On public routes, middleware passes client headers through untouched, so:

- The route **never** reads `x-verified-user-id` / `x-verified-user-email` and never uses `getAuthenticatedUserFast`, because a forged header would let anyone delete any account. `account-delete-api.test.ts` asserts that a forged header with no session gets 401.
- It does not use `getAuthenticatedUser` either. That helper requires approval, and an unapproved user may delete their own account.
- `isPublicRoute` matches by prefix, so any future route under `/api/account/*` or `/account/delete/*` is also public and must authenticate itself the same way.
- The only method is `DELETE`. It is not a CORS-simple method and Supabase SSR cookies are `SameSite=Lax`, so the cookie path is not CSRF-exposed. Never add a `GET` or form-post variant.

Success is 200 with `{ "success": true }`. Errors use `errorResponse`, so the body is `{ "error": <message>, "status": <code> }`:

| Status | `error` message                                                                       | When                                                                |
| ------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 401    | "Unauthorized"                                                                        | No valid bearer token or session                                    |
| 409    | "You are the only admin. Make another user an admin before deleting your account."    | Caller is an admin and the admin count is ≤ 1; nothing was deleted  |
| 500    | "Failed to delete your account. Please try again."                                    | Profile or admin-count lookup failed, or `deleteUser` failed        |
| 500    | "Failed to delete your attachments. Your account was not deleted — please try again." | Strict storage sweep failed; the account and its rows are untouched |

On the client, `requestAccountDeletion` maps 401 to `unauthorized` and 409 to `last-admin`. A thrown `fetch` becomes `network`. Only a 200 with a JSON body where `success === true` becomes `ok`. Everything else is `failed`, including a redirect that landed on an HTML page. If Supabase Auth is unreachable while a bearer token is being checked, the route fails closed with 401, and native clients show the "session expired" copy.

### Deletion order and retry

1. **Authenticate**, or return 401.
2. **Last-admin guard** (`rejectLastAdmin` in the route, service-role client). The route reads the caller's `profiles.is_admin`; a missing profile counts as not an admin. For an admin it counts `is_admin = true` rows, and a count ≤ 1 returns 409 with nothing touched. A lookup error or a null count goes to Sentry (`account-delete:profileLookup` / `account-delete:adminCount`) and returns 500.
3. **`deleteUserAccount(admin, userId)`** (`apps/web/src/lib/account/delete-user.ts`):
   1. **Strict storage sweep.** `removeAllUserAttachments` walks the user's `{userId}/` prefix in the `attachments` bucket (`BUCKET_NAME`) recursively. It pages `list()` 1,000 entries at a time, because the default page is only 100, and removes files in batches of up to 1,000. It throws on the first list or remove error. The helper reports that to Sentry (`delete-user-account:storage`) and returns `stage: "storage"`, which the route maps to 500. The auth user is untouched, and removal is idempotent, so a retry re-lists and finishes the job.
   2. **`admin.auth.admin.deleteUser(userId)`.** The `on delete cascade` foreign keys remove `profiles`, `notebooks`, `notes` (and `note_content_history` through `notes`), `attachments` rows and `api_keys`. An error goes to Sentry (`delete-user-account:deleteUser`) and returns `stage: "auth"`, which becomes 500.
   3. **Best-effort sweep.** `removeUserAttachments` catches an upload that landed between steps 1 and 2. Its errors go to Sentry (`remove-user-attachments:list` / `:remove`) and never fail the request.
4. **Revoke Sign in with Apple**, only if the request carried an Apple grant and the deletion succeeded. Best-effort: the outcome never changes the response ([Sign in with Apple token revocation](#sign-in-with-apple-token-revocation)).
5. Return `{ success: true }`.

**Why storage goes first.** The cascade never touches Storage, and Supabase does not allow deleting `storage.objects` with SQL, so files must be removed through the Storage API. If the auth user were deleted first and the sweep then failed, the files would be orphaned. The user could no longer sign in to retry, and no row would link the files back to them. Sweeping first keeps a failed deletion whole and retryable.

**Half state when step 3.2 fails.** Storage is already empty, but the account and its rows remain, so existing attachments show as broken until the user retries. A retry re-runs the sweep, which is cheap on an empty prefix, and then `deleteUser`. This trade-off is accepted, and the error copy asks the user to retry.

**Accepted race.** If two admins delete themselves at the same moment, both can pass the admin count and leave no admin. There is one admin today, and an admin can be restored by setting `profiles.is_admin` in the dashboard.

`/api/admin/delete-user` (pending signups only) runs the same helper after its own guards. There, a storage failure returns 500 "Failed to delete the user's attachments. The user was not deleted — please try again." and a `deleteUser` failure returns 500 "Failed to delete user".

### Local reset on mobile and desktop

`deleteAccount()` in each app's `auth-provider.tsx`:

1. Reads the session with `supabase.auth.getSession()` rather than React state, so the request carries a current access token. With no token it returns `{ status: "unauthorized" }` without sending anything.
2. Calls `requestAccountDeletion({ baseUrl: <web API origin>, accessToken })`.
3. **Any result other than `ok`** is returned as is. The session, the local WatermelonDB database and cached attachments are untouched, so the user stays signed in with their offline data.
4. **On `ok`**, there is **no pre-sign-out flush**. The account and every server row are already gone, so a sync would only fail and stall for up to `FINAL_SYNC_TIMEOUT_MS` (10 s). Unsynced local edits are discarded on purpose. The provider then calls `supabase.auth.signOut({ scope: "local" })` and runs the same reset as sign-out (#591): it clears session, approval and recovery state, then runs `clearCachedApproval`, `resetSyncState()`, `database.unsafeResetDatabase()` and `deleteAllLocalAttachments()`, each best-effort.

Both apps implement the reset as an internal `resetLocalSession(userId)` in their own `auth-provider.tsx`, shared with `signOut`. The Supabase sign-out call stays in each caller, because scope, flush and error handling differ. In `deleteAccount` the local-scope sign-out is wrapped in `try`/`catch`, so the wipe always runs once the server has confirmed the deletion. `signOut` is unchanged: it still flushes (bounded by the timeout) and still awaits the default-scope `signOut()`.

`scope: "local"` still calls Supabase's `/logout?scope=local`, which revokes the current session on the server. It does **not** keep a shared E2E user signed in. `apps/web/e2e/account-deletion.spec.ts` therefore mocks both `DELETE /api/account` and `**/auth/v1/logout**`, and any future native E2E that confirms a mocked deletion must do the same. Maestro flow `07-delete-account.yaml` only ever cancels.

### Web API origin for native apps

The canonical host is the apex `https://drafto.eu`, which serves `/api/*` directly (the MCP URL in `server.json` uses it too). Do not point the apps at `www`. A cross-host redirect makes `fetch` drop the `Authorization` header, and the request fails closed with 401.

- **Mobile:** `EXPO_PUBLIC_API_URL` → `extra.apiUrl` in `apps/mobile/app.config.ts`, read by `getApiUrl()` in the auth provider.
- **Desktop:** `API_URL` from `@env` → `apiUrl` in `apps/desktop/src/lib/config.ts`.

Both fall back to `https://drafto.eu` when the variable is unset. Supabase access tokens are project-specific, so an origin backed by the wrong Supabase project rejects the token with 401. For example, a dev build without the variable calls prod. Where to set the variables: [environments](../architecture/environments.md#web-api-origin-for-native-apps).

### Not an MCP tool

Account deletion is deliberately **not** exposed through `/api/mcp`. A destructive, irreversible action on the whole account must not be reachable with an API key. `/api/account` only accepts a Supabase session or access token, never a Drafto API key.

### Sign in with Apple token revocation

Apple requires apps that offer Sign in with Apple to revoke the user's Apple tokens when the account is deleted (App Store Review Guideline 5.1.1(v)). Drafto does this on **iOS**. The decision is recorded in [ADR-0049](../adr/0049-apple-token-revocation-on-account-deletion.md).

**There is no stored Apple token to revoke.** On iOS, `signInWithAppleNative()` sends only the identity token to Supabase, and Supabase keeps no Apple refresh token for any flow. So the client fetches a fresh authorization code at deletion time, and the server turns it into a token and revokes that.

**iOS flow.**

1. `deleteAccount()` in `apps/mobile/src/providers/auth-provider.tsx` reads the session, then calls `requestAppleRevocationGrant(user)` (`apps/mobile/src/lib/apple-revocation.ts`). Apple's sheet can stay open a while, so after it the provider reads the session again; supabase-js refreshes an access token that expired meanwhile. If that session now belongs to a different user (for example, a password-recovery link switched it), it returns `unauthorized` and deletes nothing.
   - For a user with an Apple identity (`user.identities` has `provider: "apple"`, or `app_metadata.providers` includes `apple`), it opens `AppleAuthentication.signInAsync({ requestedScopes: [] })`. The user sees Apple's "Continue with Apple ID" sheet.
   - It returns `{ authorizationCode, clientId }`, where `clientId` is `APPLE_NATIVE_CLIENT_ID` from `@drafto/shared`: the bundle ID `eu.drafto.mobile`, which the server checks against the same constant.
   - It returns `null` for anyone else, on Android, when the user cancels, or when Apple fails. The deletion then goes ahead without revocation.
2. `requestAccountDeletion` sends the grant as the JSON body `{ "apple": { ... } }`. Without a grant the request has no body, as before.
3. The route reads the grant with `readAppleRevocationGrant`. A missing body means no grant. A body that is not JSON, is over 16 KB (refused from `Content-Length`, or cut off mid-read, so it is never buffered in full), or has an invalid `apple` object is ignored and reported to Sentry (`account-delete:body`) without its contents, and the account is still deleted.
4. Only after `deleteUserAccount` succeeds, the route calls `revokeAppleSignIn` (`apps/web/src/lib/apple/revoke.ts`). The Apple identities come from the user verified at the start of the request, because the auth user is gone by then.
   1. It skips with a Sentry warning when the key is not configured (`apple-revoke:not-configured`), the client is not `eu.drafto.mobile` (`apple-revoke:unsupported-client`), or the account has no Apple identity (`apple-revoke:no-apple-identity`).
   2. It signs a 5-minute ES256 `client_secret` (`apps/web/src/lib/apple/client-secret.mjs`, the same signer as `scripts/apple-client-secret.mjs`).
   3. It POSTs the code to `https://appleid.apple.com/auth/token` (`grant_type=authorization_code`, no `redirect_uri` for native codes).
   4. It POSTs the refresh token (or the access token, if Apple issued no refresh token) to `https://appleid.apple.com/auth/revoke`. On success, Drafto disappears from the Apple ID's "Sign in with Apple" list.
   5. **Another Apple ID.** If the returned ID token's `sub` is not one of the account's Apple identities, the phone was signed in to a different Apple ID. The token is revoked anyway and the outcome is `revoked-other-apple-id`, with a warning (`apple-revoke:subject-mismatch`), because the account's own authorization stays in place. Apple's sheet may just have authorized Drafto for that Apple ID, and the person on the phone has just authenticated as it, so the flow must not leave that authorization behind. Revoking costs that Apple ID only a fresh consent prompt at its next Apple sign-in.
5. Each Apple call times out after 5 seconds, so a slow Apple adds at most 10 seconds to the response. The route exports `maxDuration = 60` and passes a deadline of that limit minus `RESPONSE_MARGIN_MS` (5 s). Each Apple call's timeout is cut to fit the deadline, and no call starts with less than a second left (`out-of-time`, `apple-revoke:out-of-time`). So a slow sweep plus a slow Apple can never stop the success response going out after the account is gone. Failures go to Sentry (`apple-revoke:token`, `:revoke`, `:client-secret`, `:unexpected`) with the HTTP status and Apple's `error` code. The code, tokens and client secret are never reported or logged. `revokeAppleSignIn` never throws, and the route returns `{ success: true }` whatever the outcome.

**Why after the deletion.** Revoking first would leave a live account whose Apple sign-in was revoked if the deletion then failed. The code stays valid for 5 minutes, which is enough. If the deletion fails, the code is simply unused; a retry asks Apple for a new one.

**Configuration.** The web API reads three optional server-only variables (`apps/web/src/env.ts`, `turbo.json` `passThroughEnv`, `.env.local.example`):

| Variable                    | Value                                                                                                             |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `APPLE_TEAM_ID`             | The Apple Developer team ID (`4J2USPSG2U`)                                                                        |
| `APPLE_SIGN_IN_KEY_ID`      | The Sign in with Apple key ID (`7BS35Y82Q6`), the same key `scripts/apple-client-secret.mjs` signs with           |
| `APPLE_SIGN_IN_PRIVATE_KEY` | The contents of `~/drafto-secrets/AuthKey_7BS35Y82Q6.p8`: a multi-line PEM, or one line with literal `\n` escapes |

Revocation runs only when all three are set (`getAppleSignInKey()` in `apps/web/src/lib/apple/config.ts`). They are set in Vercel for **Production** and **Preview**, as sensitive values. Local development and CI leave them unset, so deletion works and revocation is skipped with a warning. The client IDs are code constants, not variables: `APPLE_NATIVE_CLIENT_ID` (`eu.drafto.mobile`) in `@drafto/shared`, shared by the iOS app and the server, and `APPLE_SERVICES_ID` (`eu.drafto.web.auth`) in `client-secret.mjs`, the rotation script's default.

**Verify on a device.** Use an Apple-linked account on an iOS build that talks to the deployment you are checking.

1. Delete the account and choose Continue in Apple's sheet.
2. On the iPhone, open Settings → your name → Sign-In & Security → Sign in with Apple. Drafto is gone from the list.
3. Sentry has no `apple-revoke:*` event for that user.

Cancelling the sheet must still delete the account and leave Drafto in that list.

**Web, Android and macOS do not revoke yet** ([#705](https://github.com/JakubAnderwald/drafto/issues/705)). They sign in with Apple through Supabase's browser flow, which never gives the app an Apple code, and there is no native Apple sheet. A re-authentication step there needs a `redirect_uri` registered on the Services ID `eu.drafto.web.auth`. Apple accepts no wildcards, so it cannot be tested on Vercel previews. Their deletion is unchanged: no Apple prompt and no body. The public page `/account/delete` tells those users how to remove Drafto from their Apple ID by hand.

**Not covered:** admin deletion of pending sign-ups (`/api/admin/delete-user`) and emailed deletion requests. Neither has an Apple code.

### Emailed deletion requests (manual procedure)

People who no longer have the app, or cannot sign in, email `support@drafto.eu`. That is the only address published for this, on `/account/delete`, `/support`, `/privacy` and in `apps/mobile/store/metadata/privacy-policy.md`. Step 5.5 of `scripts/support-agent-prompt.md` always escalates these messages to `Drafto/Support/NeedsHuman` with the admin notification. It sends no reply and files no issue ([support agent → Account-deletion and data-rights requests](./support-agent.md#account-deletion-and-data-rights-requests)). The same rule escalates access, export, rectification, restriction and objection requests. Those are handled as that section describes, and never with the steps below. For a confirmed erasure or account-closure request, a person handles it **within 30 days**:

1. **Confirm the request.** `From` headers can be spoofed, so reply from Zoho to the email address registered on the Drafto account, and act only once that address confirms.
2. **Find the user in the right project.** Emailed requests almost always concern production (`tbmjbxxseonkciqovnpl`), not dev. This is a production data operation, so follow [production data safety](../operations/migrations.md). In the Supabase dashboard, open Authentication → Users, find the email and copy the user id.
3. **Never delete an admin from an emailed request.** If `profiles.is_admin` is true for that id, stop and handle it in person.
4. **Delete Storage first.** In Storage → `attachments`, delete the `{userId}/` folder with everything under it. The cascade does not touch files, and once the auth user is gone nothing links the files back to the account.
5. **Delete the auth user** in Authentication → Users. The foreign-key cascades remove the profile, notebooks, notes, attachment rows and API keys.
6. **Check** that no `{userId}/` folder has reappeared in `attachments`, in case an upload raced step 5, and remove anything found.
7. **Reply** to the requester, confirming the deletion.

Why not the admin page: `/api/admin/delete-user` only deletes **pending** users. It refuses approved users, admins and anyone who owns notebooks, notes or API keys (409). Deleting in the dashboard skips the last-admin guard and the strict sweep; steps 3, 4 and 6 stand in for them.

## Preview-only test sign-in (factory browser runner)

The dark factory's browser runner checks a PR's Vercel preview in Chrome, signed in as a dedicated test account in the dev project ([ADR-0051](../adr/0051-factory-browser-runner.md)). Claude in Chrome refuses to type a password on a non-local host, so the runner signs in by opening a one-time link instead: `https://<preview>/auth/test-sign-in?token_hash=<hashed_token>&next=/`.

- **Where the token comes from.** Bash on the Mac mini calls Supabase's admin `generate_link` with type `magiclink` for the test account, using the **dev** service-role key, and hands the returned `hashed_token` to the runner. Nobody without that key can mint a token the route accepts.
- **What the route does.** It calls `verifyOtp({ token_hash, type: "magiclink" })` through the server client, which sets the session cookies, and redirects to `next`. `next` goes through the same `sanitizeRedirectPath` as `/auth/callback`, so it stays on the preview's origin. A missing, used or expired token, or a thrown error, redirects to `/login?error=test-sign-in-failed`. The token is never logged.
- **Two gating checks**, both in `isTestSignInEnabled` (`apps/web/src/lib/auth/test-sign-in.ts`). Unless both pass, the route answers 404 before it reads any parameter:
  1. `VERCEL_ENV` is `preview`. Production deployments set `production`, and local and CI servers set nothing.
  2. The host of `NEXT_PUBLIC_SUPABASE_URL` is exactly `huhzactreblzcogqkbsd.supabase.co`, the dev project. A preview pointed at prod or any other project stays off.

  Either check alone keeps the route off on drafto.eu. Both are kept on purpose as defence in depth, so don't loosen either one or add another way to switch it on.

- **Why it is in `PUBLIC_ROUTES`.** The browser that opens the link is signed out. The E2E test in `apps/web/e2e/security.spec.ts` checks that the route answers 404 on a local server.

## Modifying safely

- **Invariants:**
  - The middleware in `apps/web/src/lib/supabase/middleware.ts` is the only server-side gate between unauthenticated / unapproved users and the app shell. Every new user-scoped route must pass through it (i.e., not be added to `PUBLIC_ROUTES` unless it is truly public).
  - The `matcher` in `apps/web/src/middleware.ts` skips static assets, `/robots.txt`, `/sitemap.xml`, the two `/.well-known` app-link files, exactly `/api/health` and `/api/mcp` (plus `/api/mcp/*`), and the MCP OAuth probe paths, so middleware never runs for them. Every middleware run bills Vercel Active CPU (4 CPU-hours per 30 days on Hobby; over that, the projects pause).
    - `/api/health` is excluded because Sentry's uptime monitor polls it.
    - `/api/mcp` is excluded because it authenticates its own Bearer API key, and a client with a bad key retries around the clock. After each 401, MCP clients also probe `/.well-known/oauth-*`, `/.well-known/openid-configuration`, then `/register`, `/authorize` and `/token`. None of those is a route, so skipping middleware turns each into a static 404 instead of a 307 to `/login` plus a second run ([ADR-0054](../adr/0054-keep-machine-traffic-out-of-session-middleware.md)).
    - Only add a path to that exclusion if it is public and needs no session. Keep the `$` anchor so lookalike paths still pass through the gate.
  - A request with no `sb-*` cookie skips the Supabase client entirely. Public routes pass through, `/` is rewritten to the landing page, and everything else redirects to `/login`, which is what the session lookup would have decided anyway. Don't put anything in that branch that a route relies on, such as the `x-verified-*` headers: those are set only after a real `getUser()`.
  - `profiles.is_approved` and `profiles.is_admin` default to `false` and are NOT user-writable. RLS cannot enforce that on its own, because a policy cannot restrict columns and "Users can update own profile" only checks row ownership. The `guard_profile_privilege_columns` trigger does it: any change to either flag from the `authenticated` / `anon` roles fails with `42501` (HTTP 403) unless `public.is_admin()` is true. Admins (through their own session) and `service_role` / `postgres` can still change them. Keep the trigger function `SECURITY INVOKER`.
  - RLS policies reference both `auth.uid()` and `is_approved` — never add a policy that only checks `auth.uid()` on user data tables.
  - `/api/admin/delete-user` permanently deletes **pending** users only. `auth.admin.deleteUser` cannot be undone, so every guard runs before it: caller is an admin, target is not the caller, target exists, and target is neither approved nor an admin (409). It also refuses (409) any account that already owns notebooks, notes or API keys, checked with the service-role client. A signup that was never approved cannot own any of those rows, because each table's insert policy requires approval. The actual deletion goes through the shared `deleteUserAccount` helper, the same one `/api/account` uses. It sweeps storage strictly first (a failure returns 500 and keeps the user), then deletes the auth user, which takes the profile and every user-owned row with it through `on delete cascade`, then runs a best-effort sweep.
  - `/api/account` is in `PUBLIC_ROUTES` and authenticates itself through `authenticateAccountRequest` only. Never switch it to `getAuthenticatedUserFast` or read `x-verified-*` headers (forgeable on public routes), and never accept a user id from the body, query or params. Any route added under `/api/account/*` or `/account/delete/*` is public by prefix match and needs the same care.
  - Account deletion order is strict storage sweep → `auth.admin.deleteUser` → best-effort sweep. Keep storage first. Never delete the auth user after a failed strict sweep.
  - The last-admin guard (409) runs before anything is deleted. The concurrent-admins race is accepted.
  - Native `deleteAccount()` touches local data **only** on `ok`, skips the pre-sign-out flush, and uses `signOut({ scope: "local" })`. `signOut()` keeps its flush and default scope. Both share one reset helper per app; do not fork it back into two copies.
  - `requestAccountDeletion` treats anything except a 200 JSON `{ success: true }` as failure. Do not loosen this, or a middleware redirect to an HTML page would read as a successful deletion and wipe the device.
  - Account deletion is not an MCP tool and must never accept an API key.
  - Sign in with Apple revocation runs only after a successful deletion and never changes its response. `revokeAppleSignIn` must not throw, must revoke whatever token it obtained (also for another Apple ID, so the flow never leaves an authorization it created), and must never put a code, token or client secret in Sentry or logs. The deletion body may only carry the Apple grant; never read an account id from it.

  - `apps/mobile/e2e/06-forgot-password.yaml` — Maestro: the recovery deep link opens in-app rather than bouncing to the website.
- **Files that must change together:**
  - Adding a new public route: update `PUBLIC_ROUTES` in `apps/web/src/lib/supabase/middleware.ts` **and** add a test case in `middleware.test.ts`.
  - Adding a `profiles` column that users must not set for themselves: add it to the guard in a new migration (`create or replace function public.guard_profile_privilege_columns()`), and extend both `profile-privilege-guard` tests.

Otherwise `deleteUser` fails, and both `DELETE /api/account` and `/api/admin/delete-user` return 500 for any user who owns a row in it, after their storage has already been swept. If only approved users can insert into the table, also add it to `USER_OWNED_TABLES` in the admin route. Update them, `remove-user-attachments.test.ts`, `account-deletion.live.test.ts`, and step 4 of the manual procedure in [Account deletion](#account-deletion), or account deletion will leave files behind.
  - Changing `DELETE /api/account` status codes or its success body: update `requestAccountDeletion` / `describeAccountDeletionFailure` in `packages/shared/src/account/request-account-deletion.ts` and its test. Both native apps and the web section act on that mapping.

  - Changing the database provider's `sync()` contract or the synced tables: `useSafeSignOut` relies on `sync()` joining a running sync and never rejecting, and `countUnsyncedChanges` lists the synced tables and the attachment `upload_status` values itself. Keep them in step on mobile and desktop.
  - Moving the macOS account actions (`app-menu.tsx` / `notebooks-sidebar.tsx`): update the Mac steps on `apps/web/src/app/account/delete/page.tsx` and `apps/web/src/app/support/page.tsx` (and `legal-pages.test.tsx` / `account-delete-page.test.tsx`), and the element checks in `apps/desktop/e2e/run-e2e.sh`.
