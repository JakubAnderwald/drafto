# Notes and Notebooks

**Status:** shipped **Updated:** 2026-11-21

## What it is

Drafto organizes user content as notes inside a flat list of notebooks. Users create, rename, and delete notebooks; create, edit, move, soft-delete, restore, and permanently delete notes. Every user owns a default "Notes" notebook auto-provisioned on first visit.

## Current state

Shipped on all four platforms: web, iOS, Android, macOS.

- Notebooks are a single flat level (no nesting). Each note belongs to exactly one notebook.
- Soft delete: `DELETE /api/notes/:id` sets `is_trashed = true` and stamps `trashed_at`. Trashed notes live in a dedicated trash view and are permanently purged after 30 days by a `pg_cron` job (`cleanup_trashed_notes()`, daily 03:00 UTC, callable only by the service role). The daily Vercel cron below removes the purged notes' files.
- Permanent delete is available from trash via `DELETE /api/notes/:id/permanent`. The route deletes the note first (only if it is the user's and trashed; `on delete cascade` takes the attachment rows), then sweeps the user's orphaned attachment files: every object in their Storage folder whose note no longer exists.
- **Deleted notes' files.** Deleting a note never removes its files by itself. SQL can't delete Storage objects, and the attachments bucket's policies only match objects under a note the user still has, so the user's own client can't remove them once the note is gone. The web app removes them with the service-role client instead (`apps/web/src/lib/storage/remove-orphaned-attachments.ts`). The service-role-only `orphaned_attachment_objects()` (`supabase/migrations/20261113000002_attachment_orphan_sweep.sql`) lists the objects whose note is gone, and the server removes them through the Storage API, at most 10,000 per run. It runs:
  - after `DELETE /api/notes/:id/permanent`, `DELETE /api/notebooks/:id` and the MCP `delete_notebook` tool, for that user's folder. It runs in `after()`, once the response is sent, and is best-effort: a failure goes to Sentry and the delete has already succeeded.
  - daily at 03:30 UTC from Vercel Cron (`apps/web/vercel.json`) at `GET /api/cron/cleanup-trash`, for everyone, after the route runs the 30-day purge again. This catches the purge's notes and mobile/desktop deletes, which sync as row deletes only. Vercel sends `Authorization: Bearer $CRON_SECRET`, so `CRON_SECRET` must be set in the Vercel project; a cron call without it is reported to Sentry. The route has `maxDuration = 60`. `/api/cron` is a public route in the middleware: the route checks the cron secret, or a signed-in admin's session for a manual `POST`, itself.
  - Deleted notes' files never count against the quota, so a user who frees space isn't refused while they wait for the sweep (see [editor.md](./editor.md) and ADR-0072).
- **Note content quota** ([ADR-0090](../adr/0090-per-user-note-content-quota.md)). Each account has a cap on the total size of its notes' content, enforced in the database so every write route meets it. It guards the free plan's shared 500 MB database.
  - **The quota** is `profiles.content_quota_bytes`: 25 MB by default (`DEFAULT_CONTENT_QUOTA_BYTES`), `NULL` for unlimited (admins). Only admins can change it; the profile privilege guard rejects anyone else with `42501`. Usage is `sum(pg_column_size(content))` over the user's notes, trashed ones included.
  - **Enforcement.** The `enforce_note_content_quota` trigger (`BEFORE INSERT OR UPDATE OF content` on `notes`) refuses a write that grows a note past the quota. It raises `P0001` with message `content_quota_exceeded` and `used_bytes=… quota_bytes=…` in `detail`. A write that doesn't grow the note (unchanged content, or shorter text) always passes, so a user over the quota can still shorten, trash and delete notes. A create re-sent through an upsert is checked once, on its UPDATE path.
  - **History** isn't counted, because users can't delete it. Instead, `archive_note_content()` drops a capped user's oldest versions once their history exceeds their content quota.
  - **Web.** These answer a refusal with `413 {error: CONTENT_QUOTA_EXCEEDED_MESSAGE, code: CONTENT_QUOTA_EXCEEDED_CODE, usedBytes, quotaBytes}` (`apps/web/src/lib/api/content-quota.ts`):
    - `PATCH /api/notes/[id]`
    - the Evernote import's `note` and `finalize` routes
    - the TickTick import, which stops the batch and sets `contentQuotaExceeded`
      The editor's auto-save shows the "Notes full" message (`contentFullMessage`) in its sync banner, and both import dialogs stop. MCP `create_note` / `update_note` return the same message as a tool error.
  - **Mobile and desktop** (`src/db/sync.ts`).
    - **A refused batch.** When the notes batch is refused, the push retries one row at a time. Every note that fits syncs; the refused notes, plus the attachments of a refused new note, go back to WatermelonDB as `experimentalRejectedIds`. They stay unsynced and go out again on a later sync.
    - **What the user sees.** The provider sets `isContentFull` and shows the message once: a toast on mobile, a "Notes Full" alert on desktop. The sync status reads "Notes full"; a clean push clears it.
    - **Old builds** don't know the refusal, so their whole notes push fails until the user frees space or updates.
  - **Usage line.** "Notes: X MB of Y MB used" (`formatContentUsage`, from `get_my_content_usage()`), with the storage line's warning and danger tones. It is on the web settings page (Notes card), in mobile Settings → Account, and in the desktop sidebar footer. Admins see and edit every user's content quota in the admin page's storage table (`admin_content_usage()`, `POST /api/admin/storage-quota` with `contentQuotaMb`).
- Deleting a notebook is blocked while it holds non-trashed notes. Web enforces this in the API (`DELETE /api/notebooks/:id` → 409 "Cannot delete notebook with notes. Move or delete notes first."); mobile and desktop enforce the same rule client-side before their WatermelonDB delete syncs (they never hit the API route). When an eligible notebook is deleted, its remaining trashed notes and attachments go with it: the server's `on delete cascade` removes them, and mobile and desktop also remove them locally so the client matches after sync. The client guard is a point-in-time check against the local copy, so a note synced from another device between the check and the delete can still slip past it (unlike the web API's DB-backed 409); mobile additionally lacks server-deletion self-heal to clean up the resulting orphan row ([#462](https://github.com/JakubAnderwald/drafto/issues/462)). Every platform's delete confirm warns that the trashed notes go too: "Trashed notes inside will be permanently deleted." Mobile and desktop show the line in every delete confirm. Web shows it only when the notebook holds trashed notes and no active ones, and keeps Delete disabled until it has checked (`apps/web/src/hooks/use-notebook-delete-impact.ts`). The notebook's notes can change while the confirm is open, so web checks again when the user confirms: if the delete would now take trashed notes with it and the line isn't on show yet (notes in it were trashed, or its active notes were moved out), the confirm shows the line instead of deleting, and the user confirms again. Web also shows the line when it can't be sure: when the check fails, or when the trash list reaches PostgREST's 1,000-row cap and may be incomplete.
- **Notebook names are unique per user** (PrimeTestLab 11035 M-01, [ADR-0097](../adr/0097-notebook-names-unique-per-user-in-app.md)). Two names clash when they match after trimming, collapsing inner spaces, Unicode normalization and lower-casing (locale-independent `toLowerCase`, so a Turkish-locale device folds "I" like the server does), so "Project Ideas", "project ideas" and " Project Ideas " are one name. The rule and the message (`A notebook named "<name>" already exists. Choose a different name.`) live in `packages/shared/src/notebooks/notebook-name.ts` (`normalizeNotebookName`, `findDuplicateNotebook`, `duplicateNotebookNameMessage`).
  - **Where it's enforced.** Mobile and desktop check the local notebook list before their WatermelonDB create or rename. Web checks its sidebar list before sending, and `POST /api/notebooks` and `PATCH /api/notebooks/:id` check the user's notebooks in the database and answer `409 {error: <message>}` (`apps/web/src/lib/api/notebook-name-conflict.ts`). The check reads every notebook the user owns, 1000 rows a page ordered by id, because PostgREST caps each response at `max_rows` (1000): an unpaged read missed a duplicate past the 1000th notebook and answered 404 for renaming one. A `PATCH` for a notebook the user doesn't own answers 404 before any name check, as MCP `rename_notebook` does. MCP `create_notebook` / `rename_notebook` return the same message as a tool error.
  - **Renames.** A notebook never clashes with itself, so changing only the case of its name goes through, and a notebook keeps the name it has even when an older duplicate exists.
  - **What the user sees.** The field stays open with the message under it (`notebook-name-error`), and editing the name clears it. Web shows the API's other create/rename failures the same way; they were silent before. On web, leaving a refused field doesn't send it again, and Escape closes it; opening another rename starts without the last one's error. The create and rename errors have their own ids (`notebook-create-name-error`, `notebook-rename-name-error`) for `aria-describedby`. On desktop, Return keeps the field focused (`submitBehavior="submit"`), and clicking away from a rename still cancels it, error included. Every name field is capped at `MAX_NOTEBOOK_NAME_LENGTH` (100).
  - **No database constraint.** Imports, the default-notebook bootstrap and offline sync can still produce a same-named notebook, and accounts may already have some; see the ADR for why.
- **Note counts** (PrimeTestLab 11035 S-03). Every notebook row shows how many notes it holds, trashed ones not counted, right-aligned in muted text ("3 notes", `formatNoteCount`).
  - **Mobile and desktop.** `useNotebookNoteCount` (`src/hooks/use-notebook-note-count.ts`) observes a WatermelonDB `observeCount()` of the notebook's non-trashed notes, so the count follows creates, trashes, restores, moves and syncs. Screen readers get the name as the row's label and the count as its value, read as "Project Ideas, 3 notes"; the label stays the bare name. On desktop the count stays put on hover and the × appears beside it; the hidden × keeps its slot, so hovering never changes a row's height.
  - **Web.** The layout prefetch and `GET /api/notebooks` embed `notes(count)` filtered with `notes.is_trashed = false`, and `withNoteCount` (`apps/web/src/lib/api/notebook-note-count.ts`) turns it into `note_count`. PostgREST applies the embedded filter to the counted rows only, so a notebook whose notes are all trashed still comes back, with 0. The sidebar refetches the list on every list refresh (`listRefreshTrigger`), which note create, trash, restore and move already bump. A new notebook starts at 0, and a rename keeps the count it had. The name sits in its own `data-testid="notebook-name"` element, which E2E helpers read instead of the row's text (`apps/web/e2e/notes.spec.ts`).
- **Notebook order.** Every platform lists notebooks newest `updated_at` first, so a notebook moves to the top when it is created or renamed. Web gets that order from `GET /api/notebooks` and the layout prefetch, and the sidebar's create and rename insert the API's row with the same comparator (`compareNewestFirst`, `apps/web/src/lib/notebooks/order.ts`), so the next refetch doesn't reorder the list ([#480](https://github.com/JakubAnderwald/drafto/issues/480)). Mobile and desktop sort their WatermelonDB query by `updated_at` desc (`src/hooks/use-notebooks.ts`).
- **Web dropdown menus.** `DropdownMenu` (`apps/web/src/components/ui/dropdown-menu.tsx`) closes on a mousedown outside it and on Escape. A consumer whose trigger toggles the menu passes the trigger as `triggerRef`, so a mousedown on the trigger isn't an outside click and its click closes the menu instead of closing and reopening it ([#480](https://github.com/JakubAnderwald/drafto/issues/480)). The app menu and the note-row actions menu both do.
- The default notebook is provisioned server-side in the App Router layout if the user has zero notebooks.
- Mobile and desktop hold a full local copy in WatermelonDB and sync via pull/push against Supabase; web reads/writes directly through the API.
- **Mobile row actions.** On iOS and Android the notebooks list, a notebook's notes list and Trash keep their row actions behind a swipe (`apps/mobile/src/components/swipeable-row.tsx`): swipe left to trash a note or delete a notebook; in Trash, swipe right to restore and left to delete for good. Long-press renames a notebook or note. Because nothing showed the swipe, each of the three lists now has (PrimeTestLab 10668 S-03):
  - A one-time hint above its rows (`apps/mobile/src/components/swipe-hint.tsx`, testIDs `swipe-hint` and `swipe-hint-dismiss`), plus one slide of the first row that shows the colour of the action under it. The slide stays on the row that was first when it armed, so a row added on top doesn't take it over, and it plays once per list and device. It doesn't run when Reduce Motion is on, stops when the hint is closed mid-slide, and hands over to a finger that grabs the row mid-slide without a jump. The hint itself goes away for good when the user closes it or first swipes a row open in that list. `useSwipeHint` (`apps/mobile/src/hooks/use-swipe-hint.ts`) keeps a "seen" and a "peeked" flag per list and per device in expo-secure-store (`apps/mobile/src/lib/swipe-hint-store.ts`, keys `drafto_swipe_hint_seen_<list>` and `drafto_swipe_hint_peeked_<list>`), like the theme preference: the app has no other key-value store outside its database, which sign-out wipes. Sign-out leaves the flags alone. On iOS they live in the Keychain, so they survive a reinstall. Empty lists show no hint.
  - Screen-reader actions on every row. TalkBack's actions menu and the VoiceOver rotor offer "Move note to Trash", "Delete notebook", "Restore note" and "Delete note permanently", and run the same confirms as the swipe buttons. The buttons under a row are labelled the same way, and they exist only while the row is swiped open or sliding, so a closed row hides nothing from a screen reader.
  - A tap on a Trash row opens Restore / Delete permanently / Cancel. Restore from this menu needs no second confirmation, because a restore can be undone; Delete permanently still asks. `trashMenuButtons` (`apps/mobile/src/lib/trash-menu-buttons.ts`) orders the buttons per platform: iOS stacks Restore, Delete permanently, then Cancel; Android puts Cancel in the neutral slot on the left and Restore in the positive one on the right.
  - Web and desktop have no swipe, so they get no hint. Their row actions are visible or appear on hover. On a touch-only pointer, where `@media (hover: none)` matches (an iPad or Android tablet browser, a phone), web shows the note-row actions button (⋮) and the notebook delete button (×) all the time, since nothing can hover over them there ([#863](https://github.com/JakubAnderwald/drafto/issues/863)). On every pointer, a web note row with actions reserves the ⋮'s width, so a long title truncates before the ⋮ instead of running under it when the row is hovered or focused, and the title doesn't move when the ⋮ appears ([#900](https://github.com/JakubAnderwald/drafto/issues/900)). On desktop, the × on a note or notebook row appears only on hover, so the row also takes the delete itself: ⌫ or ⌦ (bare or with ⌘) on the focused row (react-native-macos never moves keyboard focus on a click and leaves rows out of the Tab order, so a click on a row also focuses it, as in Apple Notes, with the focus ring off), and a named "Delete note" / "Delete notebook" action in VoiceOver's Actions menu (VO-⌘-Space). Both run the same delete as the ×, so a notebook still gets its guard and confirm. While a notebook is being renamed the row ignores them, because a ⌫ typed in the field bubbles up to it (`apps/desktop/src/hooks/use-row-delete-action.ts`, [#864](https://github.com/JakubAnderwald/drafto/issues/864)).
- The web editor watches the open note for changes made elsewhere (another device, another tab): a Supabase Realtime subscription filtered to that note, plus a re-check when the tab regains focus. When the editor has no unsaved edits the fresh content is applied in place; when it does, an inline banner offers "Discard mine" / "Keep mine" rather than overwriting. An external trash or permanent delete is surfaced the same way. See [ADR-0032](../adr/0032-web-realtime-note-sync.md).

## Cross-platform notes

- **Shared contract**: `packages/shared` owns `Database`, `NotebookRow`, `NoteRow`, and their `Insert`/`Update` variants. Every platform imports these; schema drift between Supabase and the WatermelonDB schemas is the top source of sync bugs.
- **Web** talks to Next.js route handlers which use the authenticated Supabase client. No local cache beyond a module-level `Map` in `note-editor-panel.tsx` / `note-list.tsx` fed by `use()`. The `note-list.tsx` Map is browser-only: the server render (and the first browser render, before any refresh) uses the notes `(app)/layout.tsx` prefetched, and `fetchNotes` throws if a server render reaches it, so nothing is cached across users' requests. Row timestamps render through `relative-time.tsx`, which swaps the server's text for the browser's (clock, timezone, locale) right after hydration.
- **Mobile and desktop** share identical DB code: schema, models, and sync. The desktop `apps/desktop/src/db/` directory mirrors `apps/mobile/src/db/` — keep them in sync when touching one.
- **Trash UX** is consistent across platforms, but the 30-day purge runs only server-side; local WatermelonDB records are removed via the next sync pull.
- **Default notebook** is created only by the web layout today. Mobile and desktop assume at least one notebook exists after the user's first web visit; if a user signs up and opens mobile first, sync will still surface the default notebook once web has run (or once they create one locally).

## Modifying safely

- Invariants:
  - RLS requires `profiles.is_approved = true` for all reads/writes on notebooks, notes, attachments — unapproved users see nothing.
  - `notes.user_id` and `notes.notebook_id → notebooks.user_id` must match the authenticated user; enforced in RLS `WITH CHECK`.
  - Soft delete is the default for `DELETE /api/notes/:id`. Hard delete only goes through `/api/notes/:id/permanent`.
  - `notebooks` delete rejects non-trashed children: web via a 409 in the API route, mobile/desktop via a client-side guard before the sync push issues the hard delete. Only the web 409 is race-free; the client guard is a point-in-time local check a cross-device sync can still race (#462).
  - `updated_at` is maintained by the `handle_updated_at` trigger; do not set it manually.
  - Notebook-name uniqueness is an app/API rule, not a constraint (ADR-0097): every new create or rename path must call `findDuplicateNotebook` (or `findNotebookNameConflict` on the server), and nothing may assume names are unique in the database.
- Tests that catch regressions:
  - `apps/web/__tests__/unit/notebooks-api.test.ts`, `notes-api.test.ts`, `trash-api.test.ts`, `trash-cleanup.test.ts`.
  - `apps/web/__tests__/unit/use-notebook-delete-impact.test.ts` and `apps/web/__tests__/integration/notebooks-sidebar.test.tsx` (the web delete confirm's trashed-notes warning).
  - `apps/web/e2e/notebooks.spec.ts`, `notes.spec.ts`, `cross-platform-sync.spec.ts`.
