# Editor

**Status:** shipped **Updated:** 2026-11-23

## What it is

The per-note editor where users write rich-text content. Titles and body are saved separately, debounced. Content is persisted as JSON (BlockNote on web, TipTap on mobile/desktop) and round-tripped through a shared converter so every platform can read any note.

## Current state

Shipped on all four platforms.

- **Web**: BlockNote (`@blocknote/react` + `@blocknote/mantine`). Document stored as BlockNote blocks in `notes.content` JSONB.
- **Mobile and desktop**: `@10play/tentap-editor` (TipTap inside a WebView). Documents stored as TipTap JSON strings in the local WatermelonDB `notes.content` column.
- **Auto-save**: title and body each flow through `useAutoSave` with a 500 ms debounce (`DEBOUNCE_MS` from shared). Web PATCHes `/api/notes/:id`; mobile/desktop writes to WatermelonDB and the sync loop propagates ([ADR-0048](../adr/0048-local-writes-trigger-debounced-sync.md)).
  - Web flushes edits still inside the debounce window when the page is hidden or closed (`pagehide`, `visibilitychange` → hidden), so a tab close, reload or `window.location.href` navigation keeps them. Every PATCH is sent with `keepalive: true` while autosave's own keepalive bodies in flight stay under ~60 KB; past that (a large note) it uses a plain fetch, which a closing tab can cancel. Browsers cap keepalive bodies in flight at 64 KiB per page, shared with every other keepalive request (Sentry's fetch transport sends them too), so a keepalive PATCH can still be refused: it is then sent again at once as a plain fetch, which works everywhere but a closing tab.
  - Logout awaits `flushPendingSaves()` (`apps/web/src/lib/pending-saves.ts`, capped at 3 s) before `signOut()`, because signing out deletes the session cookie before the redirect.
  - A failed save (thrown fetch or non-OK response) is put back in the queue under any newer edits and sent again with the next edit, the unmount flush or a page-hide flush; there is no retry timer. The first failure of each streak goes to Sentry (`noteId` and status, never note content); content-quota refusals aren't reported. A 401 drops the payload and sends nothing more while the redirect to `/login` runs.
- **No-op saves** (mobile and desktop, issue #654): loading a note into TenTap makes it answer with a content-update of its own. The save handlers compare each payload with the stored content and with the note's load baseline (`packages/shared/src/editor/content-save-guard.ts`) and skip a write that would change nothing. A skipped save resolves `false`, so `useAutoSave` stays `"idle"` instead of showing "Saved".
- **Web file blocks** (PrimeTestLab 11035 S-04). BlockNote's own file block already shows an icon and the name. It also writes its URL into `data-url`, so `AttachmentSizeStyles` adds a `<style>` from `buildFileBlockSizeCss` that puts the size after the name; the label's colour and spacing are in `globals.css`. For a saved note that URL is not `attachment://`: `GET /api/notes/:id` resolves every file block to a fresh signed URL before the editor gets it, while a file just uploaded in the tab keeps `attachment://<path>`. So the rule matches `data-url*=` on the same encoding-stable fragments as the native rules (`attachmentHrefFragments`, below), which appear in both forms. The sizes come from `GET /api/notes/:id/attachments`, fetched once per note by `useNoteAttachmentSizes` (`apps/web/src/components/editor/`), plus each upload made in the editor (`addAttachment`). The block schema and the stored content are unchanged.
- **Cross-format migration**: `GET /api/notes/:id` defensively converts TipTap → BlockNote on read and persists the repaired shape. Mobile/desktop convert BlockNote → TipTap on read.
- **Markdown conversion** (`packages/shared/src/editor/markdown-converter.ts`) is used by the MCP server for tool I/O and by the Evernote importer's downstream paths.
- **Attachments**: images are uploaded to Supabase Storage via signed URLs and embedded as `attachment://<path>` URIs; the API resolves these to signed URLs on read. On mobile, a picked file is saved locally, then uploaded on its own (`uploadAttachment`), then inserted, and only then is a sync started without waiting for it. "Attachment uploaded" shows only when that upload succeeded.
- **Images offline (mobile and desktop)** ([ADR-0086](../adr/0086-offline-attachment-cache.md)). Each app keeps attachment files in an on-device cache ([offline-sync.md](./offline-sync.md#offline-attachment-cache)). When a note loads, `resolveAttachmentSrc` (`src/lib/data/attachment-resolver.ts`) gives a cached image the src `file://<cache file>#drafto-attachment=<URL-encoded storage path>` with no network call; an uncached one gets a signed URL and downloads in the background; with neither (offline, never cached) it stays `attachment://` and shows as broken. Each reference has its own 8 s bound (`withResolveTimeout`), so a link or uncached image that hangs on a network with no internet can't cost cached images their local src. Links and file blocks always get a signed URL (the shared resolver passes `kind: "link"`), even when the same file is also shown as an image in the note. A just-attached image shows its local file at once (`localAttachmentSrcFor`), online or offline. On Android the editor's WebView loads TenTap's page from its HTML string with the Documents directory as its `file://` base URL (`webviewBaseURL`) and `allowFileAccess`. WebKit gives a page loaded from a string no read access to local files, so on iOS and macOS the page loads from a file instead: `useEditorPage` (`src/hooks/use-editor-page.ts`) has `ensureEditorPage` (`src/lib/editor-page.ts`) write TenTap's `editorHtml` to `attachment-cache/.editor/editor-<hash>-<length>.html` if it is missing, then the WebView gets `source={{ uri }}` and `allowingReadAccessToURL` = the `attachment-cache/` directory, and TenTap injects its boot script before the page's content loads. If the file can't be written (on desktop also when the write takes over 3 s) or fails to load, the editor falls back to the inline page (cached images may then not show). Everywhere, `originWhitelist` has `file://*`, and `allowFileAccessFromFileURLs` and `allowUniversalAccessFromFileURLs` stay off (`src/lib/editor-webview.ts`). `migrateSignedUrlsToAttachmentUrls` maps a `#drafto-attachment=` src back to `attachment://` on every save, so a device path is never stored, and opening a note with cached images and not editing it still writes nothing (#654).
- **Image render status (mobile and desktop).** `IMAGE_RENDER_STATUS_SCRIPT` (shared), injected once the editor is ready, posts each image's `img.complete && img.naturalWidth > 0` and on-screen height. `ImageRenderStatus` mirrors it as invisible accessible views: `testID` `editor-image-rendered` (as tall as the image) or `editor-image-missing` (a sliver), labelled "Image shown: <name>" or "Image not loaded: <name>". The WebView's own image nodes don't reliably reach the accessibility tree, so the Maestro flows and the QA 10668 host check read these. Screen readers would read them to real users, so both the views and the injected reporter exist only in E2E builds (`EXPO_PUBLIC_E2E_PROBES=1` on mobile, `E2E_PROBES=1` on desktop, read by `src/lib/e2e-probes.ts`; see [testing.md](../architecture/testing.md#e2e-probe-builds)).
- **Storage quota** (issue #794, [ADR-0072](../adr/0072-per-user-attachment-storage-quota.md)). Besides the 50 MB per-file limit, each account has a total attachment quota, enforced in the database so that every upload route meets it:
  - **The quota** is `profiles.storage_quota_bytes`: 50 MB by default (`DEFAULT_STORAGE_QUOTA_BYTES`), `NULL` for unlimited. Admins are set to unlimited; someone made an admin later keeps 50 MB until an admin picks Unlimited on the admin page. Only admins can change it (the profile privilege guard rejects anyone else's change with `42501`).
  - **Usage** is `sum(attachments.file_size)` for the user. Attachments on trashed notes still count until the note is deleted permanently (emptying the trash) or the trash cron purges it; both cascade the note's rows. Removing an image or file from a note does not free its bytes: the `attachments` row stays until its note is deleted, and no client deletes a single attachment. To free space, delete notes with attachments and empty the trash.
  - **Enforcement.** A `BEFORE INSERT` trigger on `attachments` refuses a row that would take usage over the quota, with the message `storage_quota_exceeded` (`STORAGE_QUOTA_EXCEEDED_CODE`); landing exactly on the quota is allowed, and an upsert of a row that already exists (the mobile/desktop retry) is let through without counting twice. The bucket's `INSERT` and `UPDATE` policies also require `can_store_attachment()`, so Storage refuses an upload with "new row violates row-level security policy" once the rows reach the quota. Its object term counts only objects under notes the user still has and allows one file (50 MB) of slack, so a client that skips the row insert is stopped at quota + 50 MB, one upload at a time (uploads that run at once, or through signed URLs created before any lands, can pass it: [ADR-0072](../adr/0072-per-user-attachment-storage-quota.md), Consequences). Deleted notes' files don't count; the web app removes them after a web or MCP delete, and daily for the trash purge and mobile/desktop deletes (see [notes-and-notebooks.md](./notes-and-notebooks.md)).
  - **Web.** `upload-url` pre-checks the quota and `confirm` maps the trigger's refusal: both answer `413 {error: STORAGE_QUOTA_EXCEEDED_MESSAGE, code: STORAGE_QUOTA_EXCEEDED_CODE, usedBytes, quotaBytes}`. The per-file 413 has no `code`. The editor and the Evernote import read the 413 with `storageQuotaErrorFromResponse`, and the editor shows the "Storage full" message (`storageFullMessage`) in its banner. On that refusal the editor also takes back the empty image or file block BlockNote made for the upload (`discardRefusedUploadBlock`), so BlockNote's own upload panel doesn't add a generic "Upload failed" beside the banner, and a dropped or pasted file doesn't leave an empty block in the note. It only touches an unfilled placeholder. **Replace** on an image already in the note hands over that image's block, which keeps its file; BlockNote's panel may then show its own "Upload failed" next to the banner. BlockNote converts an empty block in place, keeping its nested children, so such a placeholder turns back into an empty paragraph instead of being removed with them. Other upload failures keep the block, so the user can pick another file.
  - **Mobile and desktop.** A refused upload (the pre-check against `fetchStorageUsage()`, a Storage RLS refusal that a fresh usage reading confirms, or the trigger's error, recognised by `isStorageQuotaError`) puts the attachment in the terminal `quota_exceeded` upload status (`isStorageFull`). It is not retried: the client tries to remove any object it already uploaded and the user sees the "Storage full" message. A failed removal (Storage usually reports it in the result rather than throwing) is logged and doesn't change the outcome: the object stays under its note, counted in the bucket policy's object term but not in usage, until the note is deleted and the orphan sweep removes it. A usage read that hasn't answered within `STORAGE_USAGE_TIMEOUT_MS` (5 s) counts as unknown, so a stalled request never holds up saving a picked file or the upload queue; the database still decides. When the picker's own upload is the one refused, the attachment isn't inserted into the note, so no `attachment://` reference points at a file that never reaches the server. Nothing references it then, and the user still has the original file, so the picker also discards it (`discardRefusedAttachment`): it deletes the local record permanently (the server never had the row, so there is no deletion to sync) and the local copy. A queued upload refused later (e.g. one picked offline) leaves its reference in the note, and its local copy is kept, because it is the file's only copy and the note still shows it on this device. Desktop's `cleanupOrphanedFiles` keeps every file an attachment record points at, and nothing removes a `quota_exceeded` record early. Sync's server-deletion detection skips attachments that haven't uploaded. Deleting the note from the trash doesn't remove its attachment records on desktop, though deleting its notebook does. So on desktop that copy stays until the notebook is deleted or the user signs out, which deletes every local attachment file. The unsynced-changes count shown before sign-out leaves `quota_exceeded` out, because it can never sync. The user re-attaches the file after freeing space.
  - **Usage line.** Every platform shows "Storage: X MB of Y MB used" (`formatStorageUsage`), warning above 90% (`STORAGE_WARNING_RATIO`) and danger at 100%: the web settings page, mobile Settings → Account, and the desktop sidebar footer. Admins see and edit every user's quota on the web admin page (`POST /api/admin/storage-quota`).
- **Mobile/desktop layout**:
  - **Stylesheets.** Each app's stylesheet ships through `CoreBridge.configureCSS`, which TenTap injects together with every bridge's own CSS (image max-width, blockquote, task list, placeholder). Never pass `injectedJavaScript` to `<RichText>`: it replaces TenTap's script, and that script is what installs those styles.
  - **Gutter.** The body gets a horizontal-only gutter in line with the title (`EDITOR_LAYOUT_CSS`). TenTap owns `padding-bottom`.
  - **Mobile keyboard.** The `KeyboardAvoidingView` is offset by the header height (`useHeaderHeight`), and TenTap's `avoidIosKeyboard` is off, so the body is lifted once rather than padded twice. Its behaviour is `padding` on iOS and `height` on Android: Android runs edge-to-edge, so the window no longer shrinks for the keyboard.
  - **Mobile toolbar.** The toolbar theme (`src/lib/editor-theme.ts`) pins the formatting toolbar to a fixed 44 pt row on the screen's surface colour. It is rendered last, below the attachment row, so with the keyboard up it sits directly on the keyboard; with the keyboard down it sits just above the bottom safe-area inset (`editor-bottom-inset`).
  - **Toolbar always shown (mobile and desktop, PrimeTestLab 11035 S-02).** `<Toolbar hidden={false}>`. TenTap's default (`hidden` unset) hides the toolbar whenever the keyboard is down or the editor is blurred, so formatting was out of reach while reading a note, and on macOS, which has no soft keyboard, the toolbar never showed at all. TenTap's formatting commands focus the editor only inside the WebView (`editor.chain().focus()`), which left Android's WebView without native focus: the format was set, but no keyboard came up and typing went nowhere. So mobile wraps TenTap's items (`src/components/editor/toolbar-items.ts`, `NOTE_TOOLBAR_ITEMS` and `NOTE_HEADING_ITEMS`): while the editor is blurred, a formatting button first calls `editor.focus()`, which gives the WebView native focus and brings the keyboard up without moving the caret, then applies at the caret's last position. The buttons that only switch bars (Link, Heading, Close headings) don't focus. The active and disabled states stay TenTap's, so undo and redo still grey out with nothing to undo or redo. Desktop keeps TenTap's items: macOS has no soft keyboard to raise. TenTap's caret handling (`useKeyboardAccessory`) only acts while the keyboard is up, so an always-registered toolbar changes nothing there. Desktop pins the toolbar with its own theme (`apps/desktop/src/lib/editor-theme.ts`, mirroring mobile's toolbar keys), which leaves the WebView's colours alone because the desktop note body is light only. The web editor has no fixed toolbar (BlockNote's formatting toolbar floats over a selection), so it is unchanged. Maestro `03-create-edit-note.yaml`, and its inlined copy in `ios-all.yaml` and `android-all.yaml`, checks the toolbar's "Bold" and "Italic" buttons with the keyboard closed.
  - **Toolbar icons and empty notes (mobile and desktop, PrimeTestLab 11035 follow-up).** With the toolbar shown while the keyboard was down, its icons looked switched off. Two causes:
    - **A new note's empty doc had no block.** Mobile handed the editor `{type: "doc", content: []}` for a note with no content (or `[]`). TipTap loads JSON without checking the schema, so the editor held a document of size 0 with its selection at 0, where no command applies: every `canToggle*` was false, every button disabled (so a tap did nothing), and iOS could not always place a caret in the body. Both apps now pass the doc through `toEditorDoc` (`packages/shared/src/editor/format-converter.ts`), which gives a doc with no blocks one empty paragraph: mobile for `initialContent`, desktop before `setContent`. `serializeLoadedDoc` uses it too, so the no-op save baseline matches what the editor reads back. The doc's placeholder ("Write something …") now shows in a new note as well. This was on `main` before the always-shown toolbar; showing the toolbar with the keyboard down made it visible.
    - **TenTap's icon colours.** Its grey icons (white in dark mode) and its disabled look, a pale tint at 30% opacity, made an available button and a disabled one hard to tell apart. `toolbarIconStates` (mobile and desktop `editor-theme.ts`) uses the theme's text colours instead: `fgMuted` for an available button, `fg` on `bgMuted` for the active one, and `fgSubtle` at full opacity for a disabled one.
  - **File cards (mobile and desktop, PrimeTestLab 11035 S-04).** TenTap's prebuilt bundle has no `file` node, and a node it doesn't know blanks the whole note, so a file stays what `format-converter.ts` has always projected it to: a paragraph holding one linked file name. The card is CSS on that link (`buildAttachmentCardCss`, `packages/shared/src/editor/attachment-link-css.ts`): a bordered, rounded box on `bgSubtle` with a file icon drawn by a `::before` mask in `fgMuted`. Its selectors (`ATTACHMENT_LINK_SELECTORS`) match only a link whose href is a signed URL into the attachments bucket (`/storage/v1/object/sign/attachments/`) or `attachment://`, never an ordinary link or an image. TipTap renders a link whose protocol it doesn't know with an empty href, so the card shows once the link is resolved to its signed URL. Mobile ships the card in `buildEditorColorCss`, so a theme switch recolours it; desktop uses the light colours of its light-only body (`EDITOR_ATTACHMENT_CARD_CSS`). The stored content does not change.
  - **File sizes (PrimeTestLab 11035 S-04).** `useNoteAttachmentSizes` (`src/hooks/`, mirrored) observes the note's WatermelonDB `attachments` rows, and `buildAttachmentSizeCss` turns each attachment with a known size into a rule like `… a[href*="-1700000000000-0a1b2c3d"]::after { content: "1.2 MB"; }`. The rule keys on the `-<timestamp>-<random>` suffix of the storage key, which reads the same in `attachment://`, in the signed URL and in any percent-encoding of it; an older key without the suffix is matched on its whole path, raw and in each encoding Supabase may give it. Every value goes through `cssString`, which hex-escapes anything outside a plain set, so a file name can't break out of the rule or the `<style>`. The editor injects it with `editor.injectCSS(css, ATTACHMENT_SIZES_CSS_TAG)` (`"attachment-sizes"`) whenever the list changes; TenTap keeps injected stylesheets, puts them back after a WebView reload and queues them until the page is ready. Image attachments get a rule too: the rules select only file links and file blocks, never an `<img>`, so the size shows only where an image was uploaded into a web file block and is drawn as a card. Sizes use `formatFileSize` (shared): "812 KB", "1.2 MB", binary units like the storage quota.
  - **File links resolve on open and on insert.** `hasTipTapAttachmentRefs` (shared) decides whether a note needs resolving. Mobile used to look only for images, so a note with only files kept `attachment://` links that rendered with an empty href: no card and nothing to open. Both apps now insert an uploaded file with its signed URL (`withResolveTimeout(resolveAttachmentSrc)(path, "link")`, falling back to `attachment://`), so it is a card at once; a file still waiting to upload keeps `attachment://`. The insert waits at most 1.5 s for that URL (`INSERT_RESOLVE_TIMEOUT_MS`, mirrored), not the 8 s load bound, so on a stalled network the file still appears quickly, as a plain link until the note is opened again. Opening a note with only files now waits on the signed URLs like a note with images, each bounded by the 8 s timeout. On save, `tryExtractFileBlock` reads a file link shown with its signed URL (or a local src) back as its `attachment://` file block through `canonicalAttachmentUrl`, but only when the link's text is that file's name (`isAttachmentFileName`: its storage-safe form is the key's last segment, with or without the unique upload suffix; the key keeps only the first 20 characters of the extension, so `Dr. Smith referral letter scan` is compared with its extension cut the same way). A pasted signed URL, or a lone signed link worded as anything else, stays a paragraph with a link (stored as `attachment://`). A lone `attachment://` link still becomes a file block whatever its text. Before, a resolved file link saved as a paragraph with a link, so a desktop edit, or a mobile edit of a note with images, turned the web's file blocks into plain links.
  - **Mobile header.** The editor header has no title (the title field is the title), and its back label is fixed to "Notes". The notebook screen's header shows the notebook's name.

## Cross-platform notes

- **Two document formats in the wild**: `notes.content` may be BlockNote (from web) or TipTap (from mobile/desktop). The server converts TipTap → BlockNote on `GET /api/notes/:id` and persists the result, so over time notes trend toward BlockNote. Any new reader must handle both.
- **Auto-save hooks diverge** by signature. Web's hook is coupled to `fetch('/api/notes/:id')`; mobile/desktop's hook takes a generic `onSave` callback (WatermelonDB write). Both debounce with `DEBOUNCE_MS = 500`.
- **Attachments** use the `attachment://<path>` scheme everywhere. Web resolves to signed URLs server-side on read and via `useAttachmentUrlResolver` in the editor; mobile and desktop use `resolveTipTapImageUrls` with the cache-first `resolveAttachmentSrc`.
- **Attachment storage keys** (`<userId>/<noteId>/<fileName>`) are built by `buildAttachmentStoragePath` in `packages/shared/src/storage/storage-key.ts` on every platform: a storage-safe name plus a `-<timestamp>-<random>` suffix, so two files never share a key. supabase-js puts the key in the request URL unencoded, so a `#` used to cut the stored key short (the row kept the full name, and `remove()` then missed the file), and `%`, `~`, `[`, `{`, `^` failed the upload with a 400. `toStorageSafeFileName` keeps only characters checked to work end to end; widen it only after testing a new character against Storage upload, sign and signed download. The web confirm route rejects a file name that helper would change (`isStorageSafeFileName`).
- **Markdown converter** is the single path for MCP tools, Evernote import output, and any future Markdown-based integration. It does not round-trip losslessly — underline has no Markdown equivalent and is dropped.
- **Nesting between BlockNote and TipTap** (`format-converter.ts`). In TipTap only list items hold nested blocks (`listItem` and `taskItem` are `paragraph block*`). A list item's children stay nested and keep their own type and `checked` state. The children of any other block (paragraph, heading, code block, table, image, file) follow it as siblings, so a native edit flattens that one level without losing content. A code block reached through `children` becomes a paragraph holding its text, and a nested table becomes an empty paragraph, so a native save drops its cells.
- **The native editor has no code block or table node.** Mobile and desktop load tentap's prebuilt WebView bundle, whose schema has no `codeBlock`, `table`, `tableRow` or `tableCell`. Given content with a node it doesn't know, TipTap logs `[tiptap warn]: Invalid content.` and loads an empty document. That is why nested code blocks and tables become paragraphs. Top-level ones are still emitted as their own nodes, so a note that has one opens empty on mobile and desktop: a known, separate bug. `native-editor-schema.test.ts` builds the bundle's schema headlessly and checks the converter's output loads into it, survives an edit, and reads back nested.

## Modifying safely

- Invariants:
  - Titles are capped at `MAX_TITLE_LENGTH = 255` (enforced in `PATCH /api/notes/:id`).
  - Auto-save must be debounced; do not call `save()` directly from `onChange` — use `debouncedSave` / `trigger`.
  - Never write `process.env`; never instantiate Supabase clients inside editor components — use `createClient` from `@/lib/supabase/client`.
  - Content writes go through `migrateSignedUrlsToAttachmentUrls` on the server to avoid stale signed URLs being persisted. It also maps a native app's `file://…#drafto-attachment=` src back to `attachment://`; a new save path must go through it too, or a device path would sync to every other device.
  - `GET /api/notes/:id` persists converted content back to the DB; any new reader that rewrites content must be idempotent with this conversion.
  - The storage quota lives in the database, not in a client. Never hard-code 50 MB, the `storage_quota_exceeded` code or the quota messages: import them from `@drafto/shared`, and keep `DEFAULT_STORAGE_QUOTA_BYTES` in step with the column default. A new upload path must insert its `attachments` row (so the trigger sees it) and recognise the refusal with `isStorageQuotaError`.
  - `quota_exceeded` is terminal on mobile and desktop: the upload queue must never retry it.
- Tests that catch regressions:
